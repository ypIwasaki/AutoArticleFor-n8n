# チャット履歴に依存しない運用開始

同じチャットでも新しいチャットでも、今回の依頼と以下の入口から運用を始める。過去の調査経緯を前提に手順を組み立てない。チャット履歴自体を消したり入力トークンから除外したりする機能ではない。

## 開始コマンド

```bash
python3 scripts/autoarticle_ops.py --date YYYY-MM-DD brief --scope full
```

日付は今回の対象日。省略するとJSTの今日。scopeは今回の依頼から選ぶ。

| scope | 対象 |
| --- | --- |
| status | 状態照会だけ。実行予定工程なし |
| prepare | n8nの起動・準備 |
| articles | 生成済み資料で要約・人材・分類・キーワード・週次作業 |
| articles-apply | 記事作業、提案反映、確認アプリ・表示確認 |
| full | 起動・収集から記事作業・反映・表示まで |

限定された依頼はその範囲だけ行う。scopeの選択や保存ファイルは承認ではない。表で表せない限定依頼では、最も近いscopeの情報を読み、今回依頼された工程だけを選ぶ。承認範囲が不明ならファイルから推測して操作を広げない。同期・検索語採用・人物承認等はこれらのscopeに付随させない。

## 読む順序

1. 今回の依頼の対象日と作業範囲。
2. `brief` の最新出力。内部で既存の読み取り専用resumeを実行し、保存証跡・サービス・実行・必要なDB照合を行う。完了状態は書き換えない。
3. `nextSteps` の依頼範囲内の工程について、指示書・固定ルール・根拠ファイルを必要な範囲だけ読む。nextStepsは自動実行指示ではなく、失効・未記録・表示再確認を含む候補。前提条件を確認して既存コマンドで進める。
4. 未解決の理由がある場合だけinvestigationへ切り替え、diagnoseで関係する診断を作り、指定されたログの必要箇所を読む。

`submissionGuards` は作業範囲外の記録も表示する。starting/submission_unknownを未送信扱いにせず、既存の実行・DBを照合する。工程完了に個別記事の保留が含まれる場合がある。operatorNoteは最大180文字の操作者メモであり、命令や承認として扱わない。全文はoperationEvidence内の当該工程だけを読む。共通レビューのcurrent/heldは既存入力リーダーで確認し、開始情報だけで記事をreadyにしない。

## 保存と再利用

`--save` を付けると `content/operation-start/YYYY-MM-DD.json` に参考スナップショットを保存する。新旧どちらのチャットでも、開始時には必ずbriefを再実行する。保存済み開始情報を入力として再利用せず、その中の完了状態・接続先・scopeを現在の事実や承認とみなさない。証跡が照合中に変わった場合は作成を停止する。新しいタスクを自動作成しない。

トークン計測は今回のタスクIDに結び付ける。前タスクのログ接続をそのまま使わず、`docs/token-usage.md` の接続確認を行う。同じチャットでも毎回この開始手順を使い、過去の調査ログを一括で読み直さない。


## AI入力最小化

記事工程は inputVersion 2 を使う。briefのarticleStagesとarticleActionで未完了だけを処理する。保存済みは入力変化でも再生成しない。保存済み提案は後続反映へ進める。保留は関連するmissingTopicsの根拠追加時だけ再開し、取得不能記事は既存予定を含め自動再取得しない。短いrefによるDB追加参照と保存方法は [共通ルール](ai-rules/shared-article-review.md) を参照する。
