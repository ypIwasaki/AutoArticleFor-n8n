# DB集約 作業指示書

状態: フェーズ5完了（代表パターン受入・通常業務2回同期）。フェーズ6未着手。
対象: AutoArticleFor-n8nの記事処理データ
前提資料: [現状調査](database-current-state.md)、[確定方針](database-consolidation-decisions.md)

## 1. 目的

n8n内部DBとリポジトリ内ファイルに分散している記事処理データを、プロジェクト専用SQLite DBへ段階的に集約する。

情報、履歴、根拠、運用状態を失わず、専用DBを記事処理データの唯一の正本にする。移行中の既存運用を維持し、各段階で内容照合と切戻しを可能にする。

## 2. この作業に含めるもの

- 記事の基本情報
- 収集実行、収集日、検索条件、記事の出現履歴
- 本文、本文版、取得状態、取得試行、再試行予定
- 共通本文確認、事実、人物・団体、引用根拠、工程別状態
- 確認済み要約
- 記事分類
- 人材台帳、人材別名、記事・人材関係
- 記事の可否評価
- 上記データの移行、同期、比較、バックアップ、復元、互換出力

## 3. この作業に含めないもの

- AIへ渡す情報の削減
- 共通本文確認の判断基準変更
- トークン削減率の評価
- 週次レポート、生成指示書、運用ログ、運用証跡、トークン記録、キーワード候補のDB移行
- 人材候補の自動承認や検索有効化
- 保留記事の自動的な確認済み化
- 既存履歴の削除
- n8nのシステムDB全体の移行
- PostgreSQLへの移行

## 4. 守るべき原則

- 移行前の正本は既存のn8n Data Tablesと既存ファイルとする。
- 読み取り切替が完了するまで、専用DBの値を既存側へ自動的に書き戻さない。
- 同期処理は再実行可能にし、同じ処理IDを再送しても重複させない。
- 件数一致だけで移行完了としない。
- 同じURLだけを理由に記事を自動統合しない。
- 旧記事キーと出典を失わない。
- 本文取得成功と意味的レビュー完了を混同しない。
- 取得不能、部分取得、保留、未確認を確認済みに変換しない。
- DBエラー時に旧経路へ自動フォールバックして不一致を隠さない。
- 移行・照合・切替・切戻しの結果を機械可読な記録として残す。
- 移行完了まで旧DBと旧ファイルを削除しない。

## 5. 目標構成

n8nは127.0.0.1限定のローカルDBサービスへHTTPで接続する。サービスは共通DBアクセス層を使い、data/autoarticle.sqliteへ書き込む。

Pythonスクリプト、確認アプリ、週次集計、AI入力リーダーは同じ共通DBアクセス層を利用する。n8nワークフロー内へSQLiteの物理テーブル名やSQLを分散させない。

ローカルDBサービスは次を満たすこと。

- 127.0.0.1だけで待ち受ける。
- 外部ネットワークへ公開しない。
- 秘密値はGit管理しない環境変数から読む。
- 書き込み要求に処理IDを必須とする。
- 入力検証後、一つの業務操作を一つのトランザクションで保存する。
- 成功件数、更新件数、既存件数、保留件数、処理IDを返す。
- 一部成功を成功応答として返さない。
- 将来DBを変更してもn8n側の契約を維持できるようにする。

設定名は次を基本とする。

| 設定 | 用途 |
| --- | --- |
| AUTOARTICLE_DATABASE_PATH | 専用DBの場所。既定はdata/autoarticle.sqlite |
| AUTOARTICLE_DATA_SOURCE | legacyまたはproject-db |
| AUTOARTICLE_DB_SERVICE_URL | n8nが利用するローカルサービスURL |
| AUTOARTICLE_DB_SERVICE_TOKEN | ローカルサービスの認証値。Git対象外 |

## 6. DBスキーマの最低要件

物理テーブル名は実装時に確定してよいが、次の責務を分離すること。JSON文字列だけに全関係を閉じ込めず、一意性と参照整合性をDBで検証できる構造にする。

| 管理対象 | 必要な責務 |
| --- | --- |
| schema_migrations | 適用済みスキーマ版、適用日時、チェックサム |
| migration_runs | 一括移行の処理ID、入力スナップショット、開始・完了・失敗状態 |
| sync_runs | 継続同期の処理ID、対象、件数、状態、再実行情報 |
| cutover_state | 機能ごとの読み取り元、書き込み先、切替日時、切戻し状態 |
| articles | 変更されないarticle_idと記事の現在の基本情報 |
| article_identifiers | 旧記事キー、元URL、解決後URL、出典、照合状態 |
| collection_runs | 日次収集の実行、対象日、ワークフロー実行ID、検索条件 |
| article_occurrences | どの収集実行でどの記事が見つかったか、タイトル・抜粋等の観測値 |
| content_payloads | 本文・Markdown・公開メタデータ等の内容とハッシュ |
| content_fetch_attempts | 取得日時、状態、失敗理由、抽出方法、再試行予定、取得本文版 |
| article_content_versions | 記事と本文内容の版、初回・最終観測日時 |
| review_records | 入力ハッシュ、ルールハッシュ、basis、確認者、確認日時、現在状態 |
| review_task_statuses | 要約・人材・分類ごとのready、held、needs_review |
| review_facts | 確認した事実と根拠参照 |
| review_entities | 確認した人物・団体と根拠参照 |
| review_evidence | 入力項目、全文基準の文字位置、短い引用 |
| article_summaries | 確認済み要約、根拠レビュー、保存日時、現在版 |
| talents | 人材ID、表示名、所属、状態、検索有効、発見方法 |
| talent_aliases | 人材別名を一行ずつ管理 |
| article_talents | 記事・人材関係、根拠、確信度、現在状態 |
| article_classifications | 分類、根拠レビュー、確信度、分類日時、現在版 |
| classification_secondary_categories | 副カテゴリを一行ずつ管理 |
| article_feedback | 可否評価、理由、評価日時、由来、現在版 |
| consolidation_conflicts | 統合できないキー・URL・内容差分、理由、解決状態 |

最低限、次の制約を設ける。

- すべての接続でforeign_keysを有効にする。
- article_id等の内部IDは変更しないTEXT主キーとする。
- 旧記事キーは出典と種別を含めて重複を防ぐ。
- 同じ本文内容は内容ハッシュで重複保存しない。
- 同じ収集元レコードを同じ収集実行へ二重登録しない。
- 現在有効な記事・人材関係は、記事と人材の組み合わせで重複させない。
- 現在有効な分類・要約・評価は、対象と版の規則に従い一意にする。
- 工程状態、取得状態、人物状態は許可値だけを受け付ける。
- 日時はUTCのISO-8601として保存し、表示時にJSTへ変換する。
- JSONを保存する列には形式検証を行う。
- WAL、busy timeout、明示トランザクションを設定する。

## 7. 共通ツールの契約

実装では、最低限次の管理操作を提供する。名称を変更する場合も同等の責務を保つ。

- DB初期化とスキーマ更新
- 既存データの一括移行
- 既存経路からの継続同期
- 旧経路と専用DBの内容比較
- DBからの互換ファイル出力
- 整合したバックアップ作成
- バックアップの復元試験
- 機能ごとの切替状態表示
- 未解決競合の一覧表示

CLIの例:

    python3 scripts/autoarticle_db.py init
    python3 scripts/autoarticle_db.py migrate
    python3 scripts/autoarticle_db.py import-legacy
    python3 scripts/autoarticle_db.py sync
    python3 scripts/autoarticle_db.py compare
    python3 scripts/autoarticle_db.py export
    python3 scripts/autoarticle_db.py backup
    python3 scripts/autoarticle_db.py restore-check
    python3 scripts/autoarticle_db.py status

ローカルサービスには、死活確認、状態確認、記事・本文取得、レビュー保存、人材提案反映、分類反映、評価反映に必要な狭いAPIを設ける。汎用SQL実行APIは作らない。

5. 現在の確認アプリ、週次集計、AI入力リーダーの代表出力を基準値として保存する。

### 成果物

- 復元手順
- 日付付きバックアップ
- 入力ファイル台帳

- 既知の不一致一覧

6. 設定値の検証、秘密値の非表示、要求サイズ制限、処理IDの検証を追加する。

### 成果物

- スキーマとマイグレーション
- 共通DBアクセス層
- ローカルDBサービス
- DB管理CLI
- 単体テストと空DB統合テスト

## 10. フェーズ3: 既存データの一括移行

### 取込優先順位

1. 日次構造化記事から収集実行と記事出現履歴を取り込む。
2. n8n Data Tablesから現在の記事、人材、関係、分類、評価を取り込む。
3. 本文取得JSONLと本文キャッシュから本文、完全性、公開メタデータ、取得試行、再試行予定を取り込む。
4. 共通確認JSONLからレビュー、工程状態、事実、人物、引用根拠を取り込む。
5. 確認済み要約Markdownから要約と保存日を取り込む。
6. 人材・分類提案ファイルは、履歴・出典の補完に使う。反映済みDBの現在状態を無条件に上書きしない。

### 作業

- 入力ごとに出典パス、レコード位置、入力ハッシュ、取込処理版を記録する。
- article_idを作成し、旧記事キーとURLの対応を保存する。
- 同じ旧記事キーは同じarticle_idへ再利用する。
- URL一致は統合候補として記録し、タイトル・公開日・本文の整合を確認する。
- 判断不能な対応はconsolidation_conflictsへ保存する。
- 既存のpending、approved、rejected、search_enabledを保持する。
- 本文状態とレビュー状態を別々に取り込む。
- 提案と反映済み状態を区別する。
- 取込処理を中断・再実行しても、同じ入力を二重登録しない。

### 成果物

- 一括移行処理
- 取込結果JSON
- 旧キー対応表
- 未解決競合一覧
- 出典別の取込件数
- 再実行結果

### 完了条件

全入力が取込済みまたは理由付き保留であり、再実行時の追加行がゼロであること。未解決競合を自動統合しないこと。

### 中止条件

旧キー消失、根拠引用の不一致、人物状態変更、保留の格上げ、出典不明の現在値が生じた場合は停止する。

### 切戻し

専用DBを初期バックアップへ戻すか、新しい空DBへ再移行する。既存側へ書き戻さない。

## 11. フェーズ4: 内容照合

### 作業

旧経路と専用DBについて、次を全件比較する。

- 記事と収集履歴
- 旧記事キー、元URL、解決後URL
- 本文、本文ハッシュ、Markdown、公開メタデータ
- 取得状態、完全性、失敗理由、抽出方法、再試行予定
- 共通確認の入力ハッシュ、ルールハッシュ、basis、工程状態
- 事実、人物・団体、引用項目、文字位置、引用文
- 確認済み要約
- 分類と副カテゴリ
- 人材状態、検索有効、別名
- 記事・人材関係と根拠
- 記事評価
- 日次・週次・確認画面で使う集計値

既知の本文キー不一致、URL重複、関係重複は、最新基準値を再取得して比較する。2026-09-14調査時の13,624件、URL重複114組、関係重複27組は参考値であり、固定期待値として扱わない。

### 成果物

- 機械可読な全件比較結果
- 項目別件数とハッシュ
- 未解決競合一覧
- 差分の原因と処置
- 読み取り切替可否

### 完了条件

許容差分は、理由、対象、旧値、新値、承認状態が記録されたものだけとする。未説明差分が一件でもあれば次へ進まない。

### 切戻し

専用DBを読み取り対象にしていないため、既存運用を継続する。専用DBを修正して一括移行と照合を再実行する。

## 12. フェーズ5: 継続同期

### 作業

1. 現在の各業務処理が既存側へ保存を完了する。
2. 完了した処理IDと対象を専用DB同期へ渡す。
3. 同期後に対象範囲を比較する。
4. 同期成功、差分あり、同期失敗を運用状態へ保存する。
5. 差分や失敗がある場合は、その処理の読み取り切替を停止する。
6. 同じ処理IDを再送し、重複せず同じ結果を返すことを確認する。

同時に二つのDBへ直接書き込み、一方の成功だけで全体成功としない。

### 成果物

- 継続同期処理
- 処理ID台帳
- 日次同期結果
- 差分レポート
- 再実行試験

### 完了条件

通常の日次運用を複数回行い、全対象が同期・照合されること。意図的な途中失敗後に同じ処理IDで安全に再開できること。

### 切戻し

同期を停止する。既存経路を正本として運用を継続し、専用DBの不一致を修正する。

## 13. フェーズ6: 読み取り切替

次の順序を守り、一機能ずつ切り替える。

1. 照合処理
2. 確認アプリ
3. 週次集計
4. AI入力リーダー
5. n8n日次処理

各機能で次を行う。

- 切替前バックアップを作る。
- legacyとproject-dbを設定で明示選択できるようにする。
- 同じ対象・同じ日時条件で両経路の出力を比較する。
- project-dbで通常処理を実行する。
- 結果と処理時間を記録する。
- エラー時に自動フォールバックしないことを確認する。
- 切戻し試験後、次の機能へ進む。

AI入力リーダーでは、本文の量を変更せず、同じ記事、本文版、取得状態、確認状態、根拠を返すことを検証する。入力最小化は行わない。

### 成果物

- 機能ごとのデータソース切替
- 旧経路・新経路の比較試験
- 切替記録
- 切戻し手順
- 更新した運用資料

### 完了条件

全5機能で同等性と切戻しが確認され、未説明差分がないこと。

### 切戻し

問題がある機能だけlegacyへ戻す。専用DBへの同期は継続し、修正後に比較からやり直す。

## 14. フェーズ7: 書き込み元の切替

### 作業

- 専用DBサービスを記事処理データの最初の書き込み先にする。
- 記事・本文・レビュー・要約・人材関係・分類・評価を業務単位のトランザクションで保存する。
- 一定期間、専用DBから旧Data Tablesと互換ファイルへ同期する。
- 旧経路との内容比較を毎回実行する。
- 専用DBだけにデータがある状態から旧経路へ戻す試験を行う。
- n8nワークフローの応答と専用DB実データを照合する。

### 成果物

- 専用DBを利用する書き込み経路
- 旧DB・互換ファイルへの同期
- 書き込み比較結果
- 障害注入試験
- 切戻し試験結果

### 完了条件

一部保存が発生せず、再送が重複せず、旧経路へ必要なデータを同期して切り戻せること。

### 中止条件

送信結果が不明、DB内容を照合できない、旧経路との差分が説明できない、専用DBだけのデータを戻せない場合は旧書き込み停止へ進まない。

## 15. フェーズ8: 旧書き込み停止と安定確認

### 作業

1. 切替直前の完全バックアップを作り、復元を試験する。
2. n8n内部Data Tablesへの対象データ書き込みを停止する。
3. 旧Data Tablesは削除せず、読み取り専用の比較対象として残す。
4. 機械処理用JSON・JSONLの毎日生成を停止し、必要時出力へ変更する。
5. 専用DBから人向けMarkdownと必要な互換ファイルを生成する。
6. 日次運用の成功回数、差分、切戻しを記録する。
7. 30回連続で日次運用が成功するまで安定確認を続ける。
8. 不一致または切戻しが発生した場合、修正後から30回を数え直す。
9. 切替直前の完全バックアップを90日保持する。

### 成果物

- 旧書き込み停止記録
- 30回の運用記録
- 必要時エクスポート
- 最終比較結果
- 最終バックアップと復元試験
- 運用・障害対応資料

### 完了条件

確定方針に記載した全完了条件を満たし、30回連続運用が成功していること。
