# DB集約 作業指示書の決定事項

現状と数値は [DB集約に向けた現状調査資料](database-current-state.md) を参照する。この文書には、利用者と確認済みの方針だけを記録する。

## 1. 目的と作業の分離

記事処理に必要なデータをプロジェクト専用DBへ集約し、情報と挙動を失わず保存・参照できる状態にする。「AIへ渡す情報の最小化」は別の作業指示書で扱い、DB集約中はAIへ渡す内容と確認基準を意図せず変更しない。トークン削減率は本作業の完了条件に含めない。

## 2. 集約先

- プロジェクト専用SQLite DBを `data/autoarticle.sqlite` に置く。
- DB実データはGitへ登録しない。
- スキーマ、変更履歴、移行・検証処理はGit管理する。
- 共通DBアクセス層を設け、将来PostgreSQL等へ移行できる構成にする。
- n8nのワークフロー、実行履歴、認証情報等はn8n内部DBに残す。

### n8nからの接続

- n8nは127.0.0.1限定のローカルDBサービスを通して専用DBを利用する。
- サービス側で入力検証と業務単位のトランザクションを行う。
- 外部ネットワークへ公開しない。
- 認証値はGit管理しない環境変数から渡す。
- 書き込み要求には処理IDを付け、再送時の重複を防ぐ。
- スクリプト、確認アプリ、週次集計、AI入力リーダーは同じ共通DBアクセス層を利用する。

## 3. 集約対象

専用DBへ、記事基本情報、収集実行・収集履歴・検索条件、本文と版、取得状態・失敗・再試行情報、共通本文確認と引用根拠、確認済み要約、分類、人材台帳、記事・人材関係、記事評価を集約する。

週次レポート、生成指示書、運用ログ・証跡、工程別トークン記録、キーワード候補は対象外とし、ファイル管理を続ける。

## 4. DBとファイルの役割

- 専用DBを記事処理データの唯一の正本とする。
- JSON、JSONL、MarkdownはDBから生成する閲覧・交換・互換・監査用出力とする。
- ファイルの直接編集を自動的にDBへ戻さない。必要な場合は検証付き取込処理を別途定める。
- 確認済み日次要約、週間レポート、キーワード候補、工程別トークン記録、人向けMarkdownは日常的に生成する。
- 構造化記事、本文取得、共通確認のJSONLと人材・分類提案JSONは移行期間中だけ毎日生成する。
- 移行完了後、機械処理用JSON・JSONL、DB全件交換用出力、監査・バックアップ用スナップショットは必要時だけ生成する。

## 5. 記事IDと重複

- 変更されない `article_id` を新設し、旧記事キー、元URL、解決後URLを識別子対応表に残す。
- 日ごとの収集は収集履歴、取得本文は本文版として記事本体から分離する。
- 同じ旧記事キーは原則として同じ記事へ対応付ける。
- URLが同じでもタイトル・公開日・本文が矛盾する場合は自動統合しない。
- Google News URLと出版社URLはリダイレクト対応を確認できた場合だけ統合する。
- 統合前の旧キーを削除しない。判断できない重複は要確認として別記事のまま保持する。

## 6. 履歴と版

- 収集履歴と本文取得の成功・失敗・保留を保存する。
- 本文はハッシュ単位で重複排除し、変更時は旧版を上書きせず新しい版を保存する。
- HTTP 429等では空本文を複製せず、試行日時、理由、再試行予定を残す。
- 共通確認、要約、分類は根拠となった本文版とルール版を参照する。
- 旧判断を削除せず、現在有効な判断を識別する。保留を自動的に確認済みへ変更しない。

## 7. 段階移行

1. 既存の読み取り元を維持したまま、既存データを一括移行し、現在の処理完了後に専用DBへ再実行可能な継続同期を行う。
2. 記事キー、URL、本文、状態、履歴、根拠、要約、分類、人材関係、評価を内容照合する。
3. 照合処理、確認アプリ、週次集計、AI入力リーダー、n8n日次処理の順に読み取りを切り替える。
4. 専用DBを最初の書き込み先へ変更し、一定期間は旧DB・互換ファイルへ同期する。
5. 安定稼働と復元試験の後、n8n内部Data Tablesへの対象データ書き込みを停止する。

`legacy` と `project-db` を明示設定で選択可能にし、自動フォールバックで不一致を隠さない。正本の切替日時と各機能の参照先・書き込み先を記録する。

## 8. バックアップと切戻し

初回移行前、継続同期開始前、各読み取り切替前、専用DBを書き込み元にする前、旧DB書き込み停止前に復元地点を作る。

バックアップには、n8n内部DBの整合したスナップショット、専用DB、集約対象ファイル、スキーマ版、移行処理版、件数・ハッシュ台帳、切替状態を含める。機能単位で旧経路へ戻せるようにし、専用DBだけの新規データは旧経路へ同期してから書き込み先を戻す。復元手順は実際に試験し、移行直後に旧データを削除しない。

### 旧データの保持

- n8n内部DBの旧Data Tablesは、書き込み停止後も削除せず、読み取り専用の比較対象として保持する。
- 旧JSON・JSONLは、専用DBによる日次運用が30回連続で成功するまで作業ツリーに保持する。
- 切替直前の完全バックアップは90日間保持する。
- 30回の確認期間中に照合不一致または切戻しが発生した場合、修正後から成功回数を数え直す。
- 保持期間終了後の削除は別作業とし、対象一覧、容量、復元可能性を確認してから実施する。
- Gitに登録済みの過去成果物は、履歴を書き換えて消去しない。

## 9. 将来のDB切替条件

SQLiteからPostgreSQL等への切替は、単純な記事件数やDB容量だけでは決めず、次の運用要件と実測を根拠に判断する。

- 複数PC・複数サーバーから同時に書き込む必要が生じた。
- 書き込み競合やロック待ちで日次運用が繰り返し完了できず、処理時刻の調整でも解消できない。
- DBサーバー側の常時バックアップ、冗長化、自動復旧が必要になった。
- 利用者・アプリごとにDB権限を分離する必要が生じた。
- 複数環境から同じDBを利用する必要が生じた。
- 実測した処理時間、ロック発生、バックアップ要件を移行判断の記録に残す。

## 10. 完了条件

- 集約対象の全データと履歴が専用DBに保存され、本文・根拠を同じ内容・ハッシュで取得できる。
- 既知のキー不一致、URL重複、関係重複に対応先または保留理由がある。
- 新規収集、本文取得、再試行、レビュー、要約、分類、人材関係、評価を保存でき、再実行しても重複しない。
- 確認アプリ、週次集計、AI入力リーダーが旧経路と同じ結果・本文版・確認状態・根拠を返す。
- 互換ファイルをDBから再生成できる。
- 各切替地点の切戻し試験が成功する。
- 旧DB書き込み停止後も通常の日次運用が完了する。
- スキーマ作成、移行、バックアップ、復元を別環境で再実行できる。

7. 書き込み元の切替
