# フェーズ5 継続同期ドラフト（中断中）

2026-09-15現在、本番使用不可。フェーズ4確定点は `734eee2752e16fbd13db3ab8f873ffe426a1ab32`。本番DBは001～003のままであり、004の適用・継続同期・日次運用は開始していない。

## 作成済みの範囲

- `004_continuous_sync.sql`: 同期結果区分、再送回数、試行記録、変更前後と出典、旧経路の完了証跡。既存マイグレーション001～003は変更しない。
- `continuous_database_sync.py`: 一つの処理ID・要求ハッシュで、一つの業務トランザクションを保存する。異なる内容のID再使用は競合として停止。失敗時は業務更新を取り消し、失敗記録だけを別トランザクションで保存する。同じIDの成功再送は同じ結果を返し、行を追加せず再送回数だけ更新する。
- `legacy_sync_projection.py`: 保持したスナップショットから隔離DBを作り、変更前提条件と差分計画を生成する。旧行・元キー・元行ハッシュを監査履歴に残す。既存の不変履歴の上書きや保留の格上げは停止する。削除された別名・副カテゴリの履歴方針も未解決のため停止する。
- `prepare_legacy_sync.py`: 既存運用の完了状態を再確認し、完了証跡と入力を保存する。対象処理IDが一致し、入力が変わらない場合だけ同期できるようにする。
- 管理CLIに `prepare-sync`、`sync`、`sync-status` を追加した。自動実行フック・新しいDBサービスは有効にしていない。

## 中断した検証

業務入力がフェーズ4と同じ状態で隔離DBを再生成したところ、レビュー1,538件が `current` から `needs_review` に変わり、対応する移行元レコード1,538件が理由付き保留となり、新しい競合1,538件が生成された。計4,614行の差分を許容していない。

原因は、入力取得が業務データ8ディレクトリだけを対象とし、`article_review_facts.POLICY_FILES` のルールファイルをスナップショットへ含めていないこと。旧経路とフェーズ3復旧点のルールハッシュは一致するが、今回の隔離入力では `policy_hash` がNULLになる。ルールや旧データ自体の変更ではない。

中止指示に従い、原因確認と記録だけを行い、ルールファイル追加による再実行や本番への適用はしていない。46件の小規模回帰テスト成功を、実データ受入成功とは扱わない。通常の日次運用の複数回実施も未完了。

## 再開時に必要な対応

1. 同期準備の入力台帳にルール依存ファイルと実装版を含める。欠落した場合は比較・取込前に停止し、現在の作業ツリーへ暗黙にフォールバックしない。
2. ルールハッシュの再現と欠落拒否を回帰テストへ追加し、元の中断証跡を保持したまま新しい隔離候補を作る。
3. 同一入力の比較差分0件を確認する。本文欠落13件・既存競合18,305件・旧新対応を全件確認する。
4. 全対象の新規・更新・版追加・出典保存を、独立した旧経路との照合で受入確認する。下記コマンドを使用可能とするのは、その確認後。
5. 完全な同期前バックアップ・復元を確認してから004を適用する。旧業務処理完了後に `prepare-sync --operation-id ID --date YYYY-MM-DD --step STEP --output SNAPSHOT`、続いて `sync --operation-id ID --snapshot SNAPSHOT` を使う。結果不明時は `sync-status --operation-id ID` または同じ要求の再送だけを行い、新しいIDを作らない。
6. 通常の日次運用を複数回実施し、同期・照合・復元・停止時のlegacy単独運用を確認する。過去日付の再収集や合成テストを通常の日次実績に置き換えない。

コマンドは `python3 scripts/autoarticle_db.py --database DB_PATH` のサブコマンド。現在はドラフトであり、上記の問題を解決するまで本番DBには使用しない。同期を実行しなければ既存経路だけでの動作を維持する。読み取り切替・書き込み切替・自動書戻し・旧データ削除・本文補完・自動統合は含めない。
