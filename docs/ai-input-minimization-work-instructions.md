## 1. 目的と前提

作業の対象は「処理済み記事の工程別除外」「共通確認記録の工程別整理」「管理情報・重複情報の削減」。採用済み方針と確認条件の根拠は[決定事項](ai-input-minimization-decisions.md)。この指示書はそれらを実装するための手順であり、過去の会話を読み直す必要はない。

## 4. 変更の共通原則

- 要約・人材確認・分類で共通する対象選定・参照処理はまとめて実装する。工程ごとに同じ仕組みを別々に作らない。
- 記事の内部識別、本文版、確認記録、成果物との対応を維持する。URL文字列だけで記事や本文版を同一と決めない。
- 保存済み判定は「AI確認済みの成果物が永続保存されたこと」を根拠にする。DBやファイルに何か存在するだけで完了と判定しない。
- 共通確認済みのready、未確認の下書き、保存失敗・保存未確認を完了に変えない。
- 成果物の保存と後続の反映・表示確認は区別する。反映未完了でも保存済みの成果物を再生成せず、それを使って後続処理を再開する。
- 完了済み工程は本文・根拠・ルールが変わってもAIへ戻さない。過去の根拠やハッシュを更新して「現在の情報で再確認済み」と見せかけない。
- 日次出力・週次集計・確認アプリでは必要な保存済みデータを引き続き利用できるようにする。
- 本文取得不能・未確認・保留を正常な判断結果として区別する。記事の保留を、実装作業全体の中断理由にしない。

3. 変更前の入力リーダーで、対象記事・対象工程・保存状態を固定した比較用の出力を保存する。初回入力だけでなく、必要な本文の続き・根拠の追加参照も比較対象に含める。
4. フェーズ2〜3で直す保存・読み取り・運用指示の接点を短く記録する。既存項目で不足する場合だけ、工程別の保存完了や保留時点の材料を記録する最小限のDB項目追加を行う計画にする。
5. DB変更が必要な場合は既存の復旧方法を利用し、必要な復旧地点を一度確認する。新規DBの全面設計やDB移行のやり直しへ広げない。

準備の確認は一度で済ませ、次へ進む。検証用データや計測値を本番の記事判断・運用完了記録へ混入させない。

## 6. フェーズ2〜3：実装

### フェーズ2：処理対象を絞る

- 記事と工程の組み合わせごとに、保存済み、未完了、保留、本文取得不能を区別して対象を抽出する。対象一覧をAIに出す前にDB側・プログラム側で除外する。
- 保存済み成果物がある工程は、一覧・詳細入力・運用の再開候補のいずれからも再判断へ戻さない。すべて除外された場合は件数と必要な状態だけを返す。
- 要約だけ保存済みなら人材確認・分類に必要な情報は残す。反映済みテーブルだけで判定せず、保存済みで未反映の確認済み提案も判定に含める。
- 「人材の該当なし」等の確認済み結果も記事単位の対象範囲と保存完了を識別できるようにする。空の提案ファイルだけで全記事の確認完了を推定しない。
- 保存済み成果物の根拠は作成当時の本文版・確認記録に基づいて検証する。新たに作る成果物の根拠確認まで無効化しない。
- 本文取得不能になった記事は、翌日以降の自動取得・自動再試行の対象にしない。既存の本文再試行予定にも同じ選定条件を適用し、過去の失敗記録を保持する。
- タイトル・公開メタデータで実施できる工程は、その工程の既存ルールに従って対象に残す。RSS一覧収集の再試行やDB保存・反映の再開処理は変更しない。
- 本文取得不能以外の理由で保留した未完了工程は、保留理由に関係する判断材料がDBに追加された場合だけ再開する。日付、無関係な記事情報、ルールやハッシュの変化だけでは再開しない。
- 保留時点で使った根拠と不足理由を記録し、同じ材料での再開を繰り返さない。再開可否を調べるだけのために本文全体を毎回AIに渡さない。
- 再開後の判断は別履歴で追加する。材料が増えてもなお不足する場合は保留を維持し、さらに関連する材料が増えるまで再開しない。

終了条件は対象選定と状態の保存・参照が接続されていること。開発中の必要な確認は行うが、正式な6パターンの確認はフェーズ4にまとめる。

### フェーズ3：必要な情報を選び、追加参照へ接続する

共通確認が済んだ未完了工程の初回入力を次に絞る。

| 工程 | 初回入力 |
| --- | --- |
| 要約 | 主要な出来事、日時・数値、関係者、要約に必要な根拠 |
| 人材確認 | 人物・団体の名前、所属・出演等の関係、その根拠 |
| 分類 | 主題、対象との関連性、カテゴリ判断に必要な事実・根拠 |

- 各工程に短い記事参照番号、必要な状態、事実と対応する根拠を渡す。共通確認記録全体や全工程の状態・根拠を一律に添付しない。
- 既存の共通確認記録に工程との対応がない場合は、既存の事実・人物・根拠を利用して必要な対応を持たせる。過去全件をAIで分類し直す作業は追加しない。
- 初回の共通本文確認がまだ済んでいない記事は、必要な保存済み本文と根拠を読む。根拠がないのに確認済みとして処理せず、文字数削減だけを目的に判断材料を落とさない。
- 不足がある場合だけ、短い参照番号から同じ記事の該当本文版・事実・引用根拠を取得できるようにする。既存の本文部分参照を流用し、対象箇所を絞る。
- 追加参照で外部ページを取得し直さない。DBにも根拠がなければ保留を維持し、推測で埋めない。
- 短い参照番号と正式な記事ID・本文版・確認記録の対応はプログラム側で管理し、別日・別ページの同じ番号を取り違えない。保存まで同じ対応を利用する。
- 長いURL、内部ID、ハッシュ、詳細な取得履歴は通常のAI入力から省く。判断上必要な場合だけ該当情報を追加参照する。最終成果物に必要な正式なURL等はプログラム側で補う。
- 同じ入力内の重複情報をまとめ、記事・工程・根拠との対応を参照で維持する。必要な出典・引用は失わない。
- 要約・提案の保存処理、成果物確認、運用の再開案内が新しい入力形式と矛盾しないようにする。DB保存・確認アプリへの既存の経路を利用する。
- 実際に使うルール・生成指示の元・運用手順に、新しい入力と追加参照の使い方を反映する。関係する場合は運用スキルも整合させる。過去の生成指示書を全日分書き直さない。

終了条件は「対象選定→最小入力→必要時のDB追加参照→正式な参照情報の補完→成果物保存」がつながること。

## 7. フェーズ4：代表6パターンの確認

本番DBの全記事検証、全履歴の照合、DB移行の再試験は行わない。次の6パターンを少数の検証用データで確認し、同じ記事を再利用する。行内の状態違いは同じ代表例の切り替えとして扱い、記事数を増やす理由にしない。

| 番号 | パターン | 合格条件 |
| --- | --- | --- |
| 1 | 新しい記事 | 初回本文確認から要約・人材確認・分類の成果物保存へ進める。保存結果を読み出し、確認アプリで代表1件を表示できる |
| 2 | 一部工程が保存済み | 保存済み工程を除外し、未完了工程だけ処理する。保存後の本文・ルール変更でも再確認せず、未反映なら保存済み成果物で後続処理を再開できる |
| 3 | 成果物が未保存 | 共通本文確認済み、未確認の下書き、保存失敗を保存完了と誤認せず、未完了工程を残す |
| 4 | 本文取得不能 | 翌日相当の再実行でも自動再取得せず、既存の本文再試行予定からも取得しない。理由・履歴を保持し、本文不要の工程まで除外しない |
| 5 | 判断保留 | 同じ材料・無関係な更新では再入力しない。関連根拠の追加時だけ再開し、再開しても不足なら再び保留する。過去の判断と根拠が残る |
| 6 | 最小入力と追加参照 | 必要情報だけで始め、不足時に該当記事・本文版・根拠だけを追加参照できる。管理情報と重複が省かれ、成果物の正式な出典URLが正しく復元される |

パターン1と6の入力・成果物を共用してよい。アプリ表示確認は代表1件で1回とし、全画面・全記事へ広げない。既存の合格結果が現在の実装に対応していれば再利用する。

ハッシュ値や文章表現の差だけで中断しない。対象記事・本文版・根拠の対応が正しく、必要な動作に問題がないことを確認する。誤除外・根拠欠落・参照先の取り違え等は修正し、影響する代表例だけを再確認する。

## 8. 入力量の比較と作業全体の完了条件

### 比較方法

- 変更前後で同じ代表記事、同じ対象工程、同じ開始時の保存・保留状態を使う。処理後の状態だけを変更後に使い、削減効果を大きく見せない。
- 比較対象はAIに実際に渡す入力。DB内部で検索しただけの行数や全文を、AI入力のトークン数として数えない。
- 共通本文確認・要約・人材確認・分類の工程ごとに、初回入力、本文の続き・根拠等の追加参照、その合計を記録する。工程別の値と比較対象全体の合計、削減率を示す。固定の削減率は要求しない。
- 同じ数え方で変更前後を比較する。トークナイザーでの算定や文字数からの推定は方法を明記し、セッションログで観測した実使用量と区別する。文字数だけを実測トークン数として報告しない。
- 本文・管理情報等の入力データ量の比較と、会話履歴・ツール結果等を含むタスク全体の実使用量は別に記録する。入力データの削減率を、そのままタスク全体やキャッシュ入力の削減率と表現しない。
- 実使用量を記録する記事工程では、[既存の計測手順](token-usage.md)で実行中タスクのログへ接続し、当該工程の入力を読む前に開始する。キャッシュ入力は入力の内訳として扱い、二重加算しない。
- ログ未接続・未観測は未計測と記録する。過去の使用量を推測で埋めず、計測のためだけに合格済みの記事生成を繰り返さない。実測がない場合は入力データの算定・推定比較と、その制限を明記する。
- 比較は一組にまとめる。入力を変更する修正が入った場合だけ、その影響範囲を取り直す。

### 全体の完了条件

1. 第7項の6パターンが期待どおりに動き、過去の成果物・根拠・履歴を壊さず、対象記事・本文版を取り違えない。
2. 同じ代表データ・工程について、追加参照込みの合計入力量が変更前より減っている。工程別の値と削減率、測定方法、実測・推定の区別が記録されている。
3. 代表例の主要な事実・人物・分類根拠・出典が保たれる。生成文章の完全一致は求めない。
4. 確認結果を一度まとめて記録する。未実施や不合格を合格にせず、合格済みの確認を繰り返さない。

## 9. 記録・再開・作業の境界

実装担当者は、実施した内容だけを次に記録する。実装開始前に成功結果を作らない。

- docs/ai-input-minimization-progress.md：フェーズ、変更箇所、済んだ確認、残作業、再開地点。中断・不合格があれば原因と影響範囲を記す。
- docs/ai-input-minimization-verification.json：代表例の識別情報、6パターンの結果、使用した確認方法、工程別の変更前後の入力量・追加参照量・計測方法、4つの完了条件の判定。
- 本文全体、全レコード、会話本文、認証情報を検証記録に複製しない。実行内容と結果を追える最小限の参照を残す。

進捗記録はフェーズ間の承認ゲートにしない。再開時は未完了と影響範囲から続け、最初から調査・検証をやり直さない。失敗は自力で修正できる範囲で修正し、関係しない作業は継続する。

本番DBへ検証用の人物・提案・完了記録を混入させない。必要なDB項目追加や設定変更は既存の方式で行い、取得済みデータの削除・全面再取得・別DBへの再移行は行わない。RSS収集、キーワード採用、週次生成、日次運用全体の実行へ依頼範囲を広げない。

資料作成や通常の実装・修正・代表例確認のための再承認は不要。アクセス不能や未解決の外部制約など、担当者だけでは進められない事実がある場合は、具体的な対象と理由を記録して必要事項だけ確認する。利用者の既存の変更を守り、コミット・プッシュは別途依頼がある場合に行う。

完了報告では、変更内容、代表6パターンの結果、追加参照込みの入力量比較、残る制限、記録ファイルを簡潔に示す。
