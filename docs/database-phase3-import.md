# フェーズ3 一括移行の実行と保留の扱い

フェーズ3は2026-09-15に受入完了。本文欠落は固定件数ではなく元レコードの条件から判定し、今回13件を理由付き保留として保持した。既存DBへの受入補記と同一一括移行の追加0行・内容不変・復元照合を確認済み。フェーズ4は未着手。最新記録は進捗資料とdatabase-phase3-verification.jsonを参照する。

フェーズ3だけを対象とする。移行元は凍結した復旧用スナップショット、移行先は専用SQLite DB。旧経路は読み取り・書き込みともlegacyのまま維持する。

## 取込ポリシー

- n8nの記事キーで一意に一致する本文は同じ記事へ対応付ける。
- 旧キー不一致でURL候補が複数ある本文は、候補を選ばず独立した保留記事にする。
- URL候補が1件の本文は、同じ旧キー・元URLの取得キャッシュを調べる。同一キャッシュ記録のタイトル・公開日時が候補記事と一致し、空でない本文と本文ハッシュが本文DB行と一致する場合だけ対応付ける。公開日時はUTCへ正規化して比較する。
- 必須の根拠が欠ける、矛盾する、キャッシュが対応しない場合は独立した保留記事とする。チェック結果と候補の元行ハッシュを残す。
- 保留記事のIDは固定UUID名前空間と移行元テーブル・行IDから生成する。URL・候補の並び・新旧日時・文字列類似には依存しない。
- 保留記事は `articles.identity_state=held`。これは記事同一性の保留。本文が保存ハッシュと整合しない場合は、元の取得状態をsource_statusに残し、利用状態をunverified、body_integrityをheld_missing_bodyまたはheld_hash_mismatchにする。本文版参照はNULLとし、本文ペイロードを作らない。本文取得がverifiedでもレビュー完了と見なさない。
- 同じ記事・人材ペアの重複関係は全行を保持し、勝者を選ばずheldにする。元の根拠・旧関係キーはraw_jsonとsource_recordsに保存する。
- 提案・採否スナップショット・公式台帳は履歴として保存し、n8nの現在値を上書きしない。talentsの承認状態と検索有効フラグを保持する。

## 情報保存

`migration_source_files` は対象8フォルダーの全ファイルを元のバイト列・サイズ・SHA-256付きで保持する。記事処理対象と補助ファイルを区別し、業務行への投影がない説明文書などは理由付き保留として保存する。基準台帳のコード・設定等の補助ファイルは復旧用に保持するが、記事データとしては移行しない。

`source_records` は全DB行・JSONL行・JSON内のキャッシュ項目や提案等を、元パス・物理テーブル・元行位置・正規化JSONの入力ハッシュ・処理版付きで保存する。元ファイルのハッシュはバイト列、行入力ハッシュはsort_keys等を固定したJSON表現のSHA-256であり、区別して扱う。

記事との対応は `article_source_provenance`、候補と照合結果は `article_identity_assessments`、未解決事項は `consolidation_conflicts` に保存する。本文ハッシュ・取得状態・旧キー・元URLは出典レコードと専用列の両方に保持する。

本文は内容と公開メタデータ等が同一の場合だけ内容ハッシュで再利用し、本文版・取得試行は別に保持する。空本文の失敗では本文内容を複製せず、取得試行を残す。キャッシュの再試行時刻・ホスト間隔・解決URLの記録も保持する。解決URL記録を根拠に記事を自動統合しない。

レビューは入力ハッシュに合う保存済み日次入力を探し、復元できれば既存検証器で引用項目・位置・文字列と参照関係を確認する。旧ルールハッシュ・元の工程状態は変更しない。入力版や対応記事を復元できなければ記録を独立した保留記事へ保存し、レビュー全体をneeds_reviewにして理由を残す。元の判断はraw_jsonと工程別状態にそのまま残す。引用一致が確認できたレビューについても、現在ルールとの一致がなければ現在の確認済みとして扱わない。

確認済み要約は既存のMarkdown解析器を使う。保存日しかない場合のsaved_atはその日のJST午前0時をUTCへ変換した日付表現であり、実際の編集時刻を推測したものではない。元の保存日と全文は保持する。同日最新の要約が複数あれば勝者を選ばず競合に残す。

## 実行

まずn8nと記事処理が停止していること、入力のハッシュ、基準値の鮮度を確認する。変化があれば `database_phase1.py` で新しい復旧地点を作り、復元試験を完了する。古い復旧地点を削除しない。

新しい専用DBへスキーマを適用し、空DBバックアップを作る。

```sh
python3 scripts/autoarticle_db.py init
python3 scripts/autoarticle_db.py backup --output data/backups/phase3-before-import.sqlite
python3 scripts/autoarticle_db.py import-legacy --snapshot .operation-state/database-consolidation/UTC日時 --report .operation-state/database-phase3/実行ID/import-first.json
```

上の日時・実行IDは実際の復旧地点に置き換える。コマンドは移行前後にライブDBの全件基準値と集約対象ファイルのハッシュ・一覧を確認する。全書き込みは1トランザクションで、入力変化・整合性違反等では全体を取消す。

同じコマンドを同じスナップショット・専用DBへ再実行し、別の結果ファイルに記録する。処理IDは入力スナップショットの内容と移行処理版から決まり、完了済み同一処理は再保存しない。全テーブルの追加行0と論理データハッシュ一致を確認する。異なる入力・処理版による再取込は既存の移行DBへ混ぜず、別の専用DBでやり直す。

## 検証と切戻し

```sh
python3 -m unittest discover -s scripts -p 'test_*database*.py' -v
```

実データについて、全ファイルの元バイト列とハッシュ、全6テーブルの全元行、全JSONL行の入力ハッシュと内容、各取込単位のimported/heldと理由、外部キー、安定ID、候補非統合、人材状態、再実行差分を確認する。専用DBの移行後バックアップと別DBへの復元も保存・検証する。

一括移行の取消しでは旧データは影響を受けない。専用DBを切り離し、移行前の空DBバックアップから別のファイルへ復元するか、新しい空DBへ再取込する。元の復旧地点と失敗時の記録を保持する。読み取り元・書き込み先の切替は行わず、フェーズ4の内容照合も本作業には含めない。

本文欠落の受入検証は `accept_phase3_database.py` が担う。元のcontent_length/contentLengthに加え、参照キャッシュのbody_lengthを保存文字数として読み取る。元データは変更せず、専用保存列が未設定の場合だけ元値を転記し、調査結果を既存競合へ追記する。元の一括移行処理版と適用済みマイグレーションは再実行契約のため維持する。
