# AIへ渡す情報の最小化：決定事項

更新日: 2026-09-17
状態: 実装・代表確認・稼働中n8nへの反映・旧保留の追加対応が完了。最新状況は[進捗記録](ai-input-minimization-progress.md)と[検証結果](ai-input-minimization-verification.json)を参照。以下の「今回」「未着手」は方針策定当時の記録として保持する。

DB集約とは別作業として扱う。記事データをDBに保持したまま、AIへ渡す情報を必要な範囲へ絞るための決定事項を記録する。

## 1. 検討の中心

利用者が選択した次の3項目を中心に決める。

1. 処理済み記事の除外
2. 共通確認記録の工程別整理
3. 管理情報・重複情報の削減

## 2. 採用：処理済み記事は工程ごとに除外する

利用者は「工程ごとに除外」を採用した。

- 要約・人材確認・分類などの完了状態を工程ごとに扱う。
- 完了した工程への再判断用の入力を省き、未完了の工程には必要な情報を渡す。
- 全工程が完了するまで、完了済みの工程へ記事情報を渡し続けることは要求しない。
- 例：要約・人材確認が完了し分類が未完了なら、分類に必要な情報だけを渡す。
- 対象外にするのはAIへの再入力であり、記事・本文・根拠・履歴をDBから削除しない。日次出力や週次集計には必要な形で利用する。

## 3. 採用：本文を取得できなかった記事は自動再取得しない

利用者の「取得できないなら再取得は不要」という指示を採用する。YouTube等の動画ページやページ不存在など、個別記事の本文取得で取得不能となった記事を自動再取得の対象から外す。

- 取得不能となった後、翌日以降の定期的な再取得や自動再試行を行わない。
- 記事、取得結果、取得不能理由、これまでの取得履歴はDBに保持する。未確認・保留を確認済みや工程完了へ変更しない。
- 本文・根拠が増えていない取得不能記事について、本文を必要とする工程へ同じ詳細を繰り返しAI入力しない。件数・理由は必要な報告や集計に残す。
- タイトル・公開メタデータ等で実施できる工程は、その工程の既存ルールに従って扱う。本文がないことだけで記事全体を全工程から除外しない。
- 実装時は既存の本文再試行予定も自動実行の対象から外す。過去の失敗記録は削除しない。
- 対象は個別記事の本文取得。RSS一覧の収集、DB保存・反映の再開処理はこの決定の対象に含めない。
- 今回は方針の記録のみ。現在の取得処理・再試行予定・DB・運用設定は変更していない。

## 4. 採用：確認済み成果物の保存後に、その工程のAI再入力から外す

利用者は「成果物保存後に外す方法」を採用した。

- 当該工程のAIによる確認・判断が終わり、要約・人材提案・分類提案などの確認済み成果物が保存された時点で、その工程への再判断用の入力を省く。
- 後続の反映・表示確認が残っていても、AIの再判断は不要とする。後続作業は保存済み成果物を使って続ける。
- 反映の失敗だけを理由に、保存済み成果物を最初からAIに作り直させない。既存の実行・保存状態を確認して反映を再開する。
- 生成しただけの未確認の下書き、共通本文確認の根拠だけが揃った ready、成果物の保存が失敗・未確認の状態は、この除外条件を満たさない。
- AI再入力の除外と、反映・表示確認を含む運用全体の完了は分けて記録する。後続作業の未完了を隠さない。
- 保存後に本文・根拠・適用ルールが変わっても、保存済み成果物がある工程をAI再入力へ戻さない（第5項）。
- 今回は方針の記録のみであり、入力リーダーや工程状態の実装は変更していない。

## 5. 採用：保存後に情報やルールが変わっても再確認しない

利用者は、保存後に情報やルールが変わった場合でも再確認を行わない方針を採用した。

- 確認済み成果物が保存されている工程は、後から本文・根拠・判断ルールが変わってもAI入力の対象へ戻さない。再判断・再生成を自動で行わない。
- 例：分類ルールが変更されても、保存済みの分類をAIで分類し直さない。本文が別途更新されても、保存済みの要約を自動で作り直さない。
- 保存済み成果物は、作成当時の本文・根拠・適用ルールに基づく結果として保持する。過去の参照版や判断履歴を上書きし、更新後の情報で確認済みになったように扱わない。
- 更新の検知や、共通確認記録が現在の入力と異なることだけを理由に、完了済み工程のAI再確認を再開しない。保存・参照の整合性確認と、AIによる再判断は区別する。
- 新しい記事や、まだ確認済み成果物を保存していない工程の初回処理は対象に残す。
- 本文の自動再取得を行わない方針も維持する。
- 今回は方針の記録のみ。既存の変更検知・入力リーダー・DB・運用設定は変更していない。

## 6. 採用：工程別の必要情報から始め、不足時だけDBの保存済み根拠を追加参照する

利用者は「最初は必要な情報だけ渡し、不足した場合だけDB内の保存済み本文・根拠を追加参照する方式」を採用した。共通本文確認が済んでいて、これから成果物を作る未完了工程に適用する。

| 工程 | 最初に渡す情報 |
| --- | --- |
| 要約 | 主要な出来事、日時・数値、関係者、要約に必要な根拠 |
| 人材確認 | 関係する人物・団体の名前、所属・出演などの関係、その根拠 |
| 分類 | 記事の主題、対象との関連性、カテゴリ判断に必要な事実・根拠 |

- 各工程に記事の識別情報と確認状態を付け、事実と必要な根拠を対応付ける。共通確認記録全体を一律に渡さない。
- 判断材料が不足した場合だけ、同じ記事の該当本文版・保存済み事実・引用根拠をDBから追加参照する。対象と不足範囲を絞り、無関係な記事や全履歴をまとめて渡さない。
- 追加参照は未完了工程の作業中に行う。保存済み成果物がある工程の再確認・再生成は開始しない。
- 追加参照のために外部ページを取得し直さない。DB内の情報でも根拠が足りなければ未確認・保留を維持し、推測で補完しない。
- 共通確認記録をまだ作成していない新しい記事では、初回の本文確認に必要な保存済み本文・根拠を読む。記録がない状態を「確認済み事実あり」と扱わない。
- DBの元データと引用根拠は保持する。今回変更するのはAIへ渡す情報の選び方であり、記録自体を削除しない。
- 今回は方針の記録のみ。入力の抽出・追加参照機能の実装は変更していない。

## 7. 採用：管理情報・重複情報は原則省略し、必要時だけ参照する

利用者は、長いURL・内部ID・ハッシュ・詳細な取得履歴をDBに保持し、AIには短い記事参照番号と判断に必要な状態・根拠を渡す方針を採用した。

| 情報 | 通常のAI入力での扱い |
| --- | --- |
| 長いURL・内部ID | 短い記事参照番号で記事を指定する。正式なURL・内部IDとの対応はプログラム側で管理する |
| ハッシュ | 通常は渡さず、必要な整合性確認をプログラム側で行う |
| 詳細な取得履歴・管理記録 | 判断に必要な現在の状態・理由だけを渡し、詳細は必要時に参照する |
| 重複する情報 | 同じ入力内で同一内容を繰り返さず、参照で記事・工程・根拠との対応を維持する |

- 短い記事参照番号から、対象記事と該当する本文版・根拠を取り違えずに参照できるようにする。AIに正式なURLや内部IDを推測・再生成させない。
- 最終成果物で必要な正式なURL等は、保存済みの対応関係からプログラム側で補う。入力で省略したことを理由に出典情報を失わない。
- 出典の確認など判断上必要な場合だけ、該当するURL・管理情報・履歴を追加参照する。判断に必要な事実・引用根拠まで一律に省略しない。
- 追加参照は第6項と同様に未完了工程の作業中に対象を絞って行う。本文の外部再取得や、保存済み成果物がある工程の再確認は開始しない。
- 管理情報・元データ・履歴はDBに保持する。ハッシュ等をAI入力から省いても、既存の参照関係や履歴の整合性を保つ。
- 今回は方針の記録のみ。入力形式・参照番号の対応付け・成果物への補完処理は実装していない。

## 8. 採用：保留中の未完了工程は判断材料が増えた場合だけ再開する

利用者は「判断材料が増えた場合だけ再開」を採用した。本文取得不能以外の理由で保留され、まだ確認済み成果物を保存していない工程に適用する。

- 前回の判断時から材料が増えていない工程は保留を維持し、同じ情報を翌日以降に繰り返しAI入力しない。保留を工程完了として扱わない。
- 保留理由の解消に関係する事実・根拠がDBに追加された場合だけ、該当する未完了工程を再開する。無関係な情報の追加、日付・管理情報・ハッシュの変化だけでは再開しない。
- 例：同姓同名の人物を特定できず人材確認を保留した記事は、所属等の特定につながる根拠がDBに追加された場合だけ人材確認を再開する。
- 再開時は保留理由・追加された判断材料・必要な既存根拠を渡す。不足時だけ第6項に従ってDB内の保存済み本文・根拠を追加参照する。
- 再開しても根拠が不足する場合は保留を維持する。その判断時に使用した材料を記録し、さらに関連する判断材料が増えるまでは同じ材料で再開を繰り返さない。
- 過去の保留判断と当時の根拠は保持し、再開後の判断を別の履歴として追加する。現行の ready（判断に必要な根拠が揃った状態）を、成果物の作成・保存まで完了した状態と自動的に同一視しない。
- 本文の自動再取得は行わない。確認済み成果物を保存済みの工程は、判断材料が増えても再確認・再生成の対象に戻さない。
- 今回は方針の記録のみ。保留工程の抽出・再開判定・入力処理は実装していない。

## 9. 採用：代表6パターンに絞った動作確認

利用者は「代表6パターン・削減率の固定なし・影響範囲だけ再確認」という確認範囲と完了条件を採用した。本番DBの全記事を検証することは求めない。

| 番号 | 代表パターン | 確認する内容 |
| --- | --- | --- |
| 1 | 新しい記事 | 初回の本文確認から、要約・人材確認・分類の成果物保存まで進められる |
| 2 | 一部の工程が保存済み | 保存済み工程を除外し、未完了工程だけ処理する。保存後に本文・ルールが変わっても再確認しない |
| 3 | 成果物が未保存 | 共通本文確認済み・下書き作成済み・保存失敗を、成果物保存済みと誤認して除外しない |
| 4 | 本文取得不能 | 翌日相当の再実行でも自動再取得しない。取得不能理由が残り、本文不要の工程まで除外しない |
| 5 | 判断保留 | 材料が同じなら再入力せず、関連する根拠が追加された場合だけ再開する。無関係な更新では再開しない |
| 6 | 必要情報だけの入力と追加参照 | 最初は必要な情報だけを渡し、不足時に該当するDBの本文・根拠を参照できる。最終成果物の出典URLも正しく復元される |

- 各パターンは少数の検証用データで確認する。同じ記事を状態違いの確認に使い回し、確認のために大量の記事を用意しない。
- 成果物の読み出し・確認アプリの表示は、パターン1の代表例で1回確認する。
- 同じ条件での変更前後の入力量比較を1回行う。追加参照も含める。
- 今回は確認範囲の決定のみ。実装・動作確認・入力量の計測を実施済みとは扱わない。

## 10. 採用：完了条件と再確認の範囲

次の4点をすべて満たした時点で、今回の入力最小化作業を完了とする。

1. **代表6パターンが期待どおりに動く。** 過去の成果物・根拠・履歴を壊さず、対象記事や本文版を取り違えない。
2. **追加参照を含めて入力量が減る。** 同じ代表データ・同じ工程で変更前後の「初回入力＋追加参照」の合計入力トークン数を比較する。工程別の数値と削減率を記録し、実測値と推定値を区別する。固定の削減率は設けない。
3. **記事作業に必要な情報が保たれる。** 代表例の主要な事実・人物・分類根拠・出典を確認する。生成文章の完全一致は求めない。
4. **確認結果を一度まとめて記録する。** 代表例の結果と入力量の比較を記録し、未実施・不合格を合格として扱わない。合格済みの確認は繰り返さず、修正した場合も影響する範囲だけ再確認する。

- 記事・本文版・根拠の対応と必要な動作に問題がなければ、ハッシュ値や文章表現の違いだけを理由に中断しない。
- 必要な記事の誤除外、根拠の欠落、参照先の取り違えなど、動作に影響する問題を修正対象にする。
- ハッシュ値等の差だけを中断理由にしないことと、誤った参照関係や履歴の上書きを許容することは同一ではない。必要な対応関係と履歴は維持する。
- 問題の修正で再確認が必要になった場合も、影響する代表パターンや入力量比較だけをやり直し、全記事検証や影響のない確認の再実施へ拡大しない。

| フェーズ | 内容 | 作業時間の目安 |
