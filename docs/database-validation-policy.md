# DB集約の検証・完了条件（現行）

改訂日: 2026-09-16
根拠: 利用者の「代表的なパターンだけ確認し、移行自体に問題がなければハッシュ差などで中断しない」という指示。
適用範囲: フェーズ1～8の受入判定と、今後の同期・切替時の確認。過去の検証結果は書き換えない。

## 1. 判定の基本

- 移行対象は従来どおり全対象データ。検証対象を代表例に絞る。移行するデータをサンプルだけに減らさない。
- 代表パターンで保存・参照・更新・履歴保持・切戻しが期待どおりなら合格とする。本番DBの全行・全列をテストする必要はない。
- 全件意味照合、全テーブルの論理ハッシュ再計算、過去判断の全件再現、全期間の出力比較を完了条件にしない。
- フェーズ1～5の既存合格結果を再利用する。フェーズ5は f1504b1 で完了済み。基準変更を理由に再取込・再同期・再検証しない。
- 試験の範囲を先に決め、合格したら次へ進む。合格後の追加検証は、関連処理の変更または実際の不具合に対する確認に限る。
- この基準は旧文書・過去の再開指示の「全件必須」「未説明差分1件で停止」「30回成功まで完了不可」に優先する。旧記録は当時の事実として保持する。

## 2. 代表例の選び方と上限

対象機能で使うパターンだけを選ぶ。原則1パターン1件、異なる境界条件が必要な場合だけ最大3件とする。日付・URL・記事数だけ違う同一パターンを増やさず、パターンの全組合せも試験しない。同じ代表例で複数項目を確認してよい。

| パターン | 確認する内容 |
| --- | --- |
| 記事の新規保存と再送 | 旧キー・URL・記事対応を保持し、同一処理の再送で重複しない |
| 本文取得 | 正常取得、部分取得、取得不能、本文実体欠落について、適用する状態の代表各1件を選ぶ |
| 本文・元行の更新 | 新版を読め、旧版と出典も残る |
| レビューと引用 | 確認状態・本文版・根拠が一致し、保留を確認済みにしない |
| 要約・分類 | 現在版を取得でき、旧版とレビューへの参照が残る |
| 人材・関係・評価 | 状態・検索有効・別名・関係・評価を保存／取得できる |
| 重複・保留 | URL重複や対応不明を誤って統合しない |
| 判断・キャプチャ履歴 | 再評価または参照追加で旧判断・親競合を失わない |
| 集計・画面・互換出力 | 代表日／週／画面の業務上の値と表示が使える |
| 取消し・再開・復元 | 小規模DBで途中失敗を取消し、再開・復元できる |

- 本文欠落13件や既存競合の全件確認を毎回の必須項目にしない。同じ動作のものは代表例を再利用する。
- 取得状態など動作分岐が異なるものは別パターン。列ごと・IDごとにパターンを分割して実質的な全件試験に戻さない。
- 稀な更新、エラー、途中失敗は小さな隔離DBの試験でよい。本番ですべての更新種類が自然発生するまで待たない。
- 変更の影響を受けないパターンは以前の合格記録を参照する。記事追加、無関係な実装変更、文書修正だけで全試験をやり直さない。
- 問題が出た場合は同じ原因の対象・変更した処理だけを再確認する。全件試験への拡大は自動で行わない。

## 3. フェーズ別の完了条件

| フェーズ | 必要な確認 | 完了判定 |
| --- | --- | --- |
| 1 基準値とバックアップ | 必要なDB・ファイル・設定がバックアップ対象に含まれること。既存の処理件数／台帳と各データ種別の代表例、別DBへの復元1回 | 復元先で代表例を読み取れ、対象の丸ごとの取り忘れがない |
| 2 専用DB基盤 | 小規模DBで作成、再適用、基本保存・読取、重複拒否、取消し、復元。ローカル接続・認証の基本確認 | 代表操作が成功し、一部保存や無許可書込が起きない。本番全件試験は不要 |
| 3 一括移行 | 移行処理の対象・完了／失敗／保留の集計と代表行。再実行は代表入力の隔離試験1回 | 対象を取り込む処理が完了し、代表例で値・対応・状態・履歴・出典を保持。元データから存在する保留は許容 |
| 4 内容照合 | 対象機能に関連するパターン各1件。日次1日、週次1週、代表画面／AI入力 | 業務上重要な値と振る舞いが一致。影響しない差分は記録して合格 |
| 5 継続同期 | 既存側で完了した通常業務の同期1回、関連代表例。新規・更新・版・再送・取消し・復元は小規模試験で補う | 代表例の同期と重複防止・取消し・切戻しが成功。現行は通常収集と要約の2回で完了済み。追加回数や全種類の本番更新を要求しない |
| 6 読み取り切替 | 5機能の代表出力と実際の参照先。切戻し実行は異なる切替実装ごとに1回、共通処理の結果は再利用。n8nは保存済み入力で読取りと直後の利用処理を限定実行 | 全5機能で専用DBの代表出力が使え、検証済みの切替処理で旧経路へ戻せる。書込み先は維持。日次全体の実運用待ち・機能ごとの復元・全件照合は不要 |
| 7 書き込み切替 | 新規・更新・版追加を小規模DBで確認し、専用DBを先に使う通常業務1回。旧側への反映と切戻し | 代表例で部分保存・二重保存がなく、専用DBで新しく作った情報を失わず旧側へ戻せる |
| 8 旧書き込み停止 | 停止設定・必要時出力・既存の復元試験記録を確認。停止後の通常業務1回 | 専用DBで代表処理が完了し、旧側への対象書込みがない。30回連続成功は完了の待ち条件にしない |

第8フェーズ後の30回分は通常運用の成功／業務障害の既存ログで確認する。毎回の全件比較や専用の追加試験は行わない。旧ファイルの30回保持と完全バックアップの90日保持は継続し、削除は別作業とする。

### フェーズ6の重複作業を防ぐ条件（2026-09-16追加）

- 詳細は [作業指示書のフェーズ6](database-consolidation-work-instructions.md#13-フェーズ6-読み取り切替) を適用する。旧記録の「5機能それぞれで切戻しを実行」「通常処理1回」より、この短縮条件を優先する。
- 共通のDB読取り・参照元選択は一度実装・確認する。各機能では実際の参照先と固有の代表出力を確認し、設定値だけで合格にしない。切替の仕組みが異なる経路には独立した代表確認を残す。
- n8nは実際の読取りノード・接続設定でローカルサービスへの接続と直後の利用処理を確認する。保存済み入力でよく、外部収集・AI生成・後続の本番書込み・定刻実行の待機は追加しない。これは実日次運用の成功実績には数えない。
- 開始確認は既存の完了・復元記録と関連変更の確認に絞る。全件比較ツールの一括実行や、全保存ファイルの再出力を前提にしない。合格済み処理の確認は関連修正・不具合がある場合だけ繰り返す。
- 記録は database-phase6-verification.json に集約し、進捗資料には結論と参照先だけを書く。開始5～10分、実装後の確認・記録10～20分を計画目安とし、新規実装は別に見積もる。時間超過だけで中断・不適切な合格・検証の追加を行わない。業務へ影響しない差分で成功回数をリセットしない。

## 4. ハッシュ差・表現差の扱い

ハッシュの不一致そのものをフェーズ中断・不合格の理由にしない。関係する代表例の業務上の値、参照先、状態、保存・読取が正しければ、移行に影響しない差分として扱い、追加承認を求めず続行する。

| 差分 | 処置 |
| --- | --- |
| SQLiteの配置・WAL・バックアップ方式によるファイルハッシュ差 | 復元して対象の代表例を読めれば許容。ファイル全体の一致を求めない |
| JSONのキー順、空白、同値の数値表現、同じ時点の時刻表現 | パーサと業務処理が同じ値を返す代表例を確認し、許容 |
| 再送回数、監査日時、保存場所、追加の観測・出典 | 期待される変更として記録し、過去情報と業務状態が保持されていれば続行 |
| 正常な入力更新・実装修正で依存ハッシュが変化 | 変更理由と関係パターンを確認。必要ならその同期要求のスナップショットを新しく準備し、全フェーズをやり直さない |
| ハッシュ差だけがあり業務上の不具合は見つからない | 関係する代表例で値・参照・状態を確認できれば許容。未検査の全行を保証するための追加照合は不要 |
| 本文・引用の欠損、別記事への対応、誤った確認状態、消えた履歴 | 移行結果に影響するため、該当処理を止めて修正する |

本文・引用・識別キーなど意味を持つ値を、差分を消す目的で正規化／書き換えない。本文が実際に同じかは代表本文そのものと引用先で確認し、空白差を常に無意味と決めつけない。

実行時の同一ID・異内容拒否、トランザクション、参照制約、不変履歴の保護はデータ処理の契約として維持する。本方針は比較のための全件走査やハッシュ同一性を受入条件から外すもので、失敗を成功と記録する許可ではない。ハッシュ検査を含む既存ツールが無害な差分で拒否した場合は、影響するパターンで挙動を確認して比較／準備処理を限定修正できる。文書やコードに古い停止条件があるだけでユーザーの再承認待ちに戻らない。

## 5. 中断する条件と自律的に進める範囲

次の問題が実際に確認された場合、または対象操作を正しく完了したことを確認できない場合に、その機能・要求の切替／書込みを止める。

- 欠損、誤った記事対応、無断の保留解除、意図しない履歴上書き・重複。
- トランザクションの一部保存、失敗の取り残し、書込み結果不明。
- 切戻しに必要なバックアップが読めない、必要な新規データを旧側へ戻せない。
- 実際のDB破損、関連する参照不整合、秘密情報の漏出、意図しない外部公開。

停止は影響範囲に限定する。原因が分かる通常のコード修正、比較器の型・列名誤り、テストの不備は既存の作業範囲で修正し、該当試験を通して再開する。利用者の判断が必要なのは、元データの削除、業務上の値の変更、記事統合など既存方針を変える場合、または修復不能・結果不明のため進められない場合とする。

全行未検査、追加の証拠の不足、無関係なファイル変更、警告、ハッシュ差だけでは全作業を止めない。既知の保留・旧経路に元からあるエラーは、移行が原因の不具合と分ける。既知のエラー例しか試していない機能は合格とせず、小規模入力で正常系も1件確認する。

## 6. バックアップ・検証結果の再利用

- 必要なデータを含む整合したバックアップは維持する。完全バックアップを取ることと、全行を照合することを分ける。
- 読取り切替だけで業務データ・スキーマが変わらない間は同じ復旧地点を使い、機能ごとの設定だけ記録する。機能ごとに完全コピーと復元試験を繰り返さない。
- 新しい本番書込み・スキーマ更新・旧書込み停止の直前は、現在へ戻せる復旧地点を確保する。保存方式やスキーマが同じなら既存の復元試験を再利用し、新しいバックアップの読取を代表例で確認する。
- 取消し・再送・異内容拒否・障害注入は小規模隔離DBで実施する。検証のための本番更新、全要求の再送、全件再投影は行わない。
- 保存・同期そのものに必要な入力検証や制約は運用処理として残す。受入のためにそれと同じ全件検査を別途重ねない。
- 既存の比較ツールが全件専用なら、受入確認にそのまま使用せず、対象ID／期間／パターンを限定する。必要な範囲の改修だけを行う。

## 7. 検証記録

既存のフェーズ記録に、次だけを短く残す。新しい台帳・ハッシュ一覧・専用アプリを作ることは要件にしない。

- フェーズ／機能、検証対象パターン、代表IDまたは入力条件。
- 期待値と実際の結果、再利用した既存検証。
- 差分があれば、業務影響と続行／対象限定の修正判断。
- バックアップと切戻し方法への参照、完了／未完了。

「代表検証合格」と記載し、未検査の全行を合格と記載しない。全件未検査は残件に数えない。
