# DB集約 作業指示書

状態: フェーズ7完了（2026-09-17、代表パターン受入）。業務はDB先行保存・旧経路への互換反映。フェーズ8未着手。
対象: AutoArticleFor-n8nの記事処理データ
前提資料: [現状調査](database-current-state.md)、[確定方針](database-consolidation-decisions.md)

## 1. 目的

n8n内部DBとリポジトリ内ファイルに分散している記事処理データを、プロジェクト専用SQLite DBへ段階的に集約する。

情報、履歴、根拠、運用状態を失わず、専用DBを記事処理データの唯一の正本にする。移行中の既存運用を維持し、各段階で内容照合と切戻しを可能にする。

## 2. この作業に含めるもの

- 記事の基本情報
- 収集実行、収集日、検索条件、記事の出現履歴
- 本文、本文版、取得状態、取得試行、再試行予定
- 共通本文確認、事実、人物・団体、引用根拠、工程別状態
- 確認済み要約
- 記事分類
- 人材台帳、人材別名、記事・人材関係
- 記事の可否評価
- 上記データの移行、同期、比較、バックアップ、復元、互換出力

## 3. この作業に含めないもの

- AIへ渡す情報の削減
- 共通本文確認の判断基準変更
- トークン削減率の評価
- 週次レポート、生成指示書、運用ログ、運用証跡、トークン記録、キーワード候補のDB移行
- 人材候補の自動承認や検索有効化
- 保留記事の自動的な確認済み化
- 既存履歴の削除
- n8nのシステムDB全体の移行
- PostgreSQLへの移行

## 4. 守るべき原則

- 移行前の正本は既存のn8n Data Tablesと既存ファイルとする。
- 読み取り切替が完了するまで、専用DBの値を既存側へ自動的に書き戻さない。
- 同期処理は再実行可能にし、同じ処理IDを再送しても重複させない。
- 件数一致だけで移行完了としない。
- 同じURLだけを理由に記事を自動統合しない。
- 旧記事キーと出典を失わない。
- 本文取得成功と意味的レビュー完了を混同しない。
- 取得不能、部分取得、保留、未確認を確認済みに変換しない。
- DBエラー時に旧経路へ自動フォールバックして不一致を隠さない。
- 移行・照合・切替・切戻しの結果を機械可読な記録として残す。
- 移行完了まで旧DBと旧ファイルを削除しない。

## 4.1. 現行の検証方針（2026-09-16改訂）

全フェーズの完了判定は [代表パターンの検証・完了条件](database-validation-policy.md) に従う。各パターン原則1件、必要な境界例だけ最大3件とし、既存合格結果を再利用する。全データの移行は行うが、本番全データの全行・全列テストは行わない。

移行結果に影響しないハッシュ差・表現差は記録して続行する。過去の指示にある「全件照合」「差分1件で中断」「30回成功まで未完了」は現行の完了条件にしない。業務に影響する問題だけ、対象処理を修正・再確認する。

フェーズ1～5は完了済み。今回の条件改訂でやり直さず、フェーズ6以降へ適用する。条件の変更だけでは業務経路を切り替えない。

## 5. 目標構成

n8nは127.0.0.1限定のローカルDBサービスへHTTPで接続する。サービスは共通DBアクセス層を使い、data/autoarticle.sqliteへ書き込む。

Pythonスクリプト、確認アプリ、週次集計、AI入力リーダーは同じ共通DBアクセス層を利用する。n8nワークフロー内へSQLiteの物理テーブル名やSQLを分散させない。

ローカルDBサービスは次を満たすこと。

- 127.0.0.1だけで待ち受ける。
- 外部ネットワークへ公開しない。
- 秘密値はGit管理しない環境変数から読む。
- 書き込み要求に処理IDを必須とする。
- 入力検証後、一つの業務操作を一つのトランザクションで保存する。
- 成功件数、更新件数、既存件数、保留件数、処理IDを返す。
- 一部成功を成功応答として返さない。
- 将来DBを変更してもn8n側の契約を維持できるようにする。

設定名は次を基本とする。

| 設定 | 用途 |
| --- | --- |
| AUTOARTICLE_DATABASE_PATH | 専用DBの場所。既定はdata/autoarticle.sqlite |
| AUTOARTICLE_DATA_SOURCE | legacyまたはproject-db |
| AUTOARTICLE_DB_SERVICE_URL | n8nが利用するローカルサービスURL |
| AUTOARTICLE_DB_SERVICE_TOKEN | ローカルサービスの認証値。Git対象外 |

## 6. DBスキーマの最低要件

物理テーブル名は実装時に確定してよいが、次の責務を分離すること。JSON文字列だけに全関係を閉じ込めず、一意性と参照整合性をDBで検証できる構造にする。

| 管理対象 | 必要な責務 |
| --- | --- |
| schema_migrations | 適用済みスキーマ版、適用日時、チェックサム |
| migration_runs | 一括移行の処理ID、入力スナップショット、開始・完了・失敗状態 |
| sync_runs | 継続同期の処理ID、対象、件数、状態、再実行情報 |
| cutover_state | 機能ごとの読み取り元、書き込み先、切替日時、切戻し状態 |
| articles | 変更されないarticle_idと記事の現在の基本情報 |
| article_identifiers | 旧記事キー、元URL、解決後URL、出典、照合状態 |
| collection_runs | 日次収集の実行、対象日、ワークフロー実行ID、検索条件 |
| article_occurrences | どの収集実行でどの記事が見つかったか、タイトル・抜粋等の観測値 |
| content_payloads | 本文・Markdown・公開メタデータ等の内容とハッシュ |
| content_fetch_attempts | 取得日時、状態、失敗理由、抽出方法、再試行予定、取得本文版 |
| article_content_versions | 記事と本文内容の版、初回・最終観測日時 |
| review_records | 入力ハッシュ、ルールハッシュ、basis、確認者、確認日時、現在状態 |
| review_task_statuses | 要約・人材・分類ごとのready、held、needs_review |
| review_facts | 確認した事実と根拠参照 |
| review_entities | 確認した人物・団体と根拠参照 |
| review_evidence | 入力項目、全文基準の文字位置、短い引用 |
| article_summaries | 確認済み要約、根拠レビュー、保存日時、現在版 |
| talents | 人材ID、表示名、所属、状態、検索有効、発見方法 |
| talent_aliases | 人材別名を一行ずつ管理 |
| article_talents | 記事・人材関係、根拠、確信度、現在状態 |
| article_classifications | 分類、根拠レビュー、確信度、分類日時、現在版 |
| classification_secondary_categories | 副カテゴリを一行ずつ管理 |
| article_feedback | 可否評価、理由、評価日時、由来、現在版 |
| consolidation_conflicts | 統合できないキー・URL・内容差分、理由、解決状態 |

最低限、次の制約を設ける。

- すべての接続でforeign_keysを有効にする。
- article_id等の内部IDは変更しないTEXT主キーとする。
- 旧記事キーは出典と種別を含めて重複を防ぐ。
- 同じ本文内容は内容ハッシュで重複保存しない。
- 同じ収集元レコードを同じ収集実行へ二重登録しない。
- 現在有効な記事・人材関係は、記事と人材の組み合わせで重複させない。
- 現在有効な分類・要約・評価は、対象と版の規則に従い一意にする。
- 工程状態、取得状態、人物状態は許可値だけを受け付ける。
- 日時はUTCのISO-8601として保存し、表示時にJSTへ変換する。
- JSONを保存する列には形式検証を行う。
- WAL、busy timeout、明示トランザクションを設定する。

## 7. 共通ツールの契約

実装では、最低限次の管理操作を提供する。名称を変更する場合も同等の責務を保つ。

- DB初期化とスキーマ更新
- 既存データの一括移行
- 既存経路からの継続同期
- 旧経路と専用DBの内容比較
- DBからの互換ファイル出力
- 整合したバックアップ作成
- バックアップの復元試験
- 機能ごとの切替状態表示
- 未解決競合の一覧表示

CLIの例:

    python3 scripts/autoarticle_db.py init
    python3 scripts/autoarticle_db.py migrate
    python3 scripts/autoarticle_db.py import-legacy
    python3 scripts/autoarticle_db.py sync
    python3 scripts/autoarticle_db.py compare
    python3 scripts/autoarticle_db.py export
    python3 scripts/autoarticle_db.py backup
    python3 scripts/autoarticle_db.py restore-check
    python3 scripts/autoarticle_db.py status

ローカルサービスには、死活確認、状態確認、記事・本文取得、レビュー保存、人材提案反映、分類反映、評価反映に必要な狭いAPIを設ける。汎用SQL実行APIは作らない。

## 10. フェーズ3: 既存データの一括移行

### 作業・成果物

収集履歴、旧DBの現行情報、本文・取得履歴、レビュー・引用、要約、人材・分類・評価をすべて移行対象にする。安定した記事ID、旧キー、出典と元行、状態、旧版、未解決競合を保存する。移行処理が出す対象・成功・失敗・保留の集計と旧キー対応を記録する。

### 完了条件

対象の移行処理が完了し、関連する代表例で記事対応・内容・状態・履歴・出典を保持していること。対象種別の丸ごとの未取込や処理失敗がないことを結果集計で確認する。既知の保留は理由が記録されていれば合格を妨げない。再実行の重複防止は小規模な代表入力で確認し、本番全体の再移行を試験にしない。

### 中止・切戻し

実際の欠損、誤った対応付け、履歴消失、保留格上げなどを検出した対象を修正する。旧側への自動書戻しはしない。必要時は専用DBを復旧地点へ戻す。

### 完了条件

### 中止・切戻し

移行による欠損・誤対応・誤状態・必要な出力の失敗を検出した範囲だけを修正し、該当パターンを再確認する。既存運用を継続する。

## 13. フェーズ6: 読み取り切替

本節は2026-09-16の短縮指示を反映した現行手順。旧手順の「各機能で切戻しを実行」「日次の通常処理1回」は要求しない。共通処理を一度実装し、切替は下表の順序で一機能ずつ行う。5機能を5組の独立した実装・準備・検証作業として扱わない。

### 開始確認と実装範囲

1. フェーズ5の完了記録、現在の参照先・書込み先、関連コード・スキーマ・業務データの変更有無、既存復旧地点の所在と利用可能性を確認する。既存の完了・復元記録を使い、全ファイル走査・全ハッシュ再計算・復元の再実行はしない。基準以降の変更は関連箇所だけ確認し、既知の未同期データを無視して合格にしない。
2. 5機能の入口、共通化する読取り処理、固有処理、代表例を短く決める。週次集計がAI入力リーダーの load_day を使う既存構造を利用し、記事・本文・レビューの取得と参照元の選択を重複実装しない。確認アプリとローカルDBサービスも共通DBアクセス層を使う。大規模な再設計は追加しない。
3. 共通読取りを実装した後、各入口の接続・出力整形を変更する。既存の表示・集計ロジックを再利用する。n8nはローカルDBサービス経由とし、対象は日次処理の人材台帳・記事評価等の読取り部分に限定する。

業務上必要な期間の集計・読取りは従来どおり行う。短縮するのは重複実装と受入のための追加検査であり、実際に扱う記事や出力項目を減らす変更ではない。

### 実装を短縮する具体的な分担

共通DBアクセス層の上に、専用DBの値を既存関数の入力形式へ変換する小さな読取りモジュールを置く。表示・集計・AI入力の組立ては既存関数を使う。既存の読取り関数へ選択処理を追加すれば足りる場合は、新しい抽象化を増やさない。

| 実装単位 | 利用する機能・再利用する箇所 |
| --- | --- |
| 共通の参照元選択 | 既存の cutover_state を使い、機能ごとの legacy／project-db の選択を一箇所で解決。別の設定台帳・管理画面を新設しない |
| 記事・本文・レビュー等の取得と入力形式への変換 | AI入力と週次集計で共有。read_ai_inputs.load_day、article_review_facts.load_reviews の入口を接続し、article_view、resolve_review、週次の集計・整形は再利用する。評価・分類・要約など集約対象の補助入力も該当する取得関数からDBを読む |
| 台帳・関係・評価等の取得と入力形式への変換 | 確認アプリとn8nで共有。確認アプリは既存の描画用データの組立てを再利用し、要約・分類・本文取得情報など集約対象の補助読取りも切り替える |
| n8nへの接続 | 既存 autoarticle_db_service.py の認証・HTTP処理を使い、必要な読取り口だけ追加。日次の人材台帳・記事評価ノードを接続し、既存の検索条件・除外処理へ同じ形式の値を渡す |
| 照合への接続 | 上の取得結果を代表比較へ渡す小さな入口とする。既存の比較関数を再利用し、新しい照合システムを作らない |

compare_phase4_outputs.py にあるDB値から確認アプリ用の行を作る対応付けは、再利用候補として使える。ただし旧DBのテーブル一覧、試験用の応答差替え、全ファイル出力に依存する部分は業務読取りへ持ち込まない。旧形式への変換はメモリ上で行い、保存ファイル一式を作り直す方式にしない。

DB内の元JSONは互換項目の復元に利用できるが、過去の保存ファイルや raw_json を丸ごと返して切替完了としない。現在の状態・有効版、対象日の収集履歴、旧キーとの対応は専用DBの該当レコードから取得する。保留・本文版・引用先を維持し、移行対象外のルール・キーワード候補等は従来のファイル参照を続ける。

実装順は「共通取得・変換 → 各入口の接続」とする。業務経路の切替順は下表のままとし、実装の共用と一斉切替を混同しない。読取り対応のためだけのスキーマ再設計、新しいDBサービス、汎用ORM、UI改修、集計式の改変、AI入力最小化、全件エクスポート機構は追加しない。実際に不足する項目があれば、その取得処理だけを補う。

読取り対応・切替の実装は共通化と既存形式の維持を前提に60～90分を計画目標とする（実測見積もりや完了保証ではなく、開始確認・受入確認の15～30分は別枠）。超過が見込まれる場合は「5機能あるため」と一括計上せず、未実装の取得項目・変換・接続を具体的に挙げて見積もりを更新する。時間を合わせるために対象機能や補助入力を残したまま完了扱いにしない。

### 代表確認
