# DB集約 作業指示書の決定事項

現状と数値は [DB集約に向けた現状調査資料](database-current-state.md) を参照する。この文書には、利用者と確認済みの方針だけを記録する。

## 1. 目的と作業の分離

記事処理に必要なデータをプロジェクト専用DBへ集約し、情報と挙動を失わず保存・参照できる状態にする。「AIへ渡す情報の最小化」は別の作業指示書で扱い、DB集約中はAIへ渡す内容と確認基準を意図せず変更しない。トークン削減率は本作業の完了条件に含めない。

## 2. 集約先

- プロジェクト専用SQLite DBを `data/autoarticle.sqlite` に置く。
- DB実データはGitへ登録しない。
- スキーマ、変更履歴、移行・検証処理はGit管理する。
- 共通DBアクセス層を設け、将来PostgreSQL等へ移行できる構成にする。
- n8nのワークフロー、実行履歴、認証情報等はn8n内部DBに残す。

### n8nからの接続

- n8nは127.0.0.1限定のローカルDBサービスを通して専用DBを利用する。
- サービス側で入力検証と業務単位のトランザクションを行う。
- 外部ネットワークへ公開しない。
- 認証値はGit管理しない環境変数から渡す。
- 書き込み要求には処理IDを付け、再送時の重複を防ぐ。
- スクリプト、確認アプリ、週次集計、AI入力リーダーは同じ共通DBアクセス層を利用する。

## 3. 集約対象

専用DBへ、記事基本情報、収集実行・収集履歴・検索条件、本文と版、取得状態・失敗・再試行情報、共通本文確認と引用根拠、確認済み要約、分類、人材台帳、記事・人材関係、記事評価を集約する。

週次レポート、生成指示書、運用ログ・証跡、工程別トークン記録、キーワード候補は対象外とし、ファイル管理を続ける。

## 4. DBとファイルの役割

- 専用DBを記事処理データの唯一の正本とする。
- JSON、JSONL、MarkdownはDBから生成する閲覧・交換・互換・監査用出力とする。
- ファイルの直接編集を自動的にDBへ戻さない。必要な場合は検証付き取込処理を別途定める。
- 確認済み日次要約、週間レポート、キーワード候補、工程別トークン記録、人向けMarkdownは日常的に生成する。
- 構造化記事、本文取得、共通確認のJSONLと人材・分類提案JSONは移行期間中だけ毎日生成する。
- 移行完了後、機械処理用JSON・JSONL、DB全件交換用出力、監査・バックアップ用スナップショットは必要時だけ生成する。

## 5. 記事IDと重複

- 変更されない `article_id` を新設し、旧記事キー、元URL、解決後URLを識別子対応表に残す。
- 日ごとの収集は収集履歴、取得本文は本文版として記事本体から分離する。
- 同じ旧記事キーは原則として同じ記事へ対応付ける。
- URLが同じでもタイトル・公開日・本文が矛盾する場合は自動統合しない。
- Google News URLと出版社URLはリダイレクト対応を確認できた場合だけ統合する。
- 統合前の旧キーを削除しない。判断できない重複は要確認として別記事のまま保持する。

## 6. 履歴と版

- 収集履歴と本文取得の成功・失敗・保留を保存する。
- 本文はハッシュ単位で重複排除し、変更時は旧版を上書きせず新しい版を保存する。
- HTTP 429等では空本文を複製せず、試行日時、理由、再試行予定を残す。
- 共通確認、要約、分類は根拠となった本文版とルール版を参照する。
- 旧判断を削除せず、現在有効な判断を識別する。保留を自動的に確認済みへ変更しない。

## 7. 段階移行

1. 既存の読み取り元を維持したまま、既存データを一括移行し、現在の処理完了後に専用DBへ再実行可能な継続同期を行う。
2. 記事キー、URL、本文、状態、履歴、根拠、要約、分類、人材関係、評価を内容照合する。
3. 照合処理、確認アプリ、週次集計、AI入力リーダー、n8n日次処理の順に読み取りを切り替える。
4. 専用DBを最初の書き込み先へ変更し、一定期間は旧DB・互換ファイルへ同期する。
5. 安定稼働と復元試験の後、n8n内部Data Tablesへの対象データ書き込みを停止する。

`legacy` と `project-db` を明示設定で選択可能にし、自動フォールバックで不一致を隠さない。正本の切替日時と各機能の参照先・書き込み先を記録する。

## 8. バックアップと切戻し

初回移行前、継続同期開始前、専用DBを書き込み元にする前、旧DB書き込み停止前に復元地点を確保する。読み取り切替前は有効な復元地点を確認し、業務データ・スキーマが変わらない間は同じ地点を共有する。機能ごとの完全コピー・復元試験は繰り返さない。

バックアップには、n8n内部DBの整合したスナップショット、専用DB、集約対象ファイル、スキーマ版、移行処理版、件数・ハッシュ台帳、切替状態を含める。機能単位で旧経路へ戻せるようにし、専用DBだけの新規データは旧経路へ同期してから書き込み先を戻す。復元手順は一度実際に試験し、同じ方式・スキーマでは結果を再利用する。新しいバックアップは代表例の読取で確認し、全件比較を必須にしない。移行直後に旧データを削除しない。

### 旧データの保持

- n8n内部DBの旧Data Tablesは、書き込み停止後も削除せず、読み取り専用の比較対象として保持する。
- 旧JSON・JSONLは、専用DBによる日次運用が30回連続で成功するまで作業ツリーに保持する。
- 切替直前の完全バックアップは90日間保持する。
- 30回は完了後の通常業務ログで確認する。業務障害により正常運用へ戻せなかった場合や切戻しを行った場合だけ、旧ファイル保持のための連続成功回数を数え直す。ハッシュ・表現差など業務影響のない差分ではリセットしない。これはフェーズ8の完了条件ではない。
- 保持期間終了後の削除は別作業とし、対象一覧、容量、復元可能性を確認してから実施する。
- Gitに登録済みの過去成果物は、履歴を書き換えて消去しない。

## 9. 将来のDB切替条件

SQLiteからPostgreSQL等への切替は、単純な記事件数やDB容量だけでは決めず、次の運用要件と実測を根拠に判断する。

- 複数PC・複数サーバーから同時に書き込む必要が生じた。
- 書き込み競合やロック待ちで日次運用が繰り返し完了できず、処理時刻の調整でも解消できない。
- DBサーバー側の常時バックアップ、冗長化、自動復旧が必要になった。
- 利用者・アプリごとにDB権限を分離する必要が生じた。
- 複数環境から同じDBを利用する必要が生じた。
- 実測した処理時間、ロック発生、バックアップ要件を移行判断の記録に残す。

## 10. 完了条件

[検証・完了条件の現行基準](database-validation-policy.md)で代表例を確認して判定する。全データを移行する方針と、本番全データを検証しない方針を区別する。

- 移行処理の対象・成否・保留集計に対象種別の取り忘れや未処理の失敗がなく、関連代表例で内容・旧キー・状態・履歴・出典を保持する。
- 新規、更新、版追加、再送、取消し、復元を代表試験で確認する。稀な更新や障害は小規模DBの試験でよい。
- 確認アプリ、週次、AI入力、n8n等の対象機能で代表出力と実際の参照先を確認し、検証済みの切替処理で明示的に旧経路へ戻せる。切戻し試験は異なる実装ごとに1回行い、共通処理を機能数だけ再試験しない。
- 互換ファイルを代表データから生成でき、専用DBから旧経路へ新規データを失わず戻せる。
- 旧書込み停止後に通常業務1回が成功し、停止設定と代表例の保存・出力を確認できる。
- 全件・全期間の比較、全論理ハッシュ一致、全種類の本番更新、30回連続成功を完了条件にしない。成功済み検証は再利用する。

ハッシュ・日時・表現の違いなど、関係代表例で移行結果に影響しないと確認できる差分は記録して続行する。差分の追加承認や全件再調査は要求しない。実際の欠損、誤対応、部分保存、履歴消失、書込み結果不明、復元不能は該当操作の停止・修正対象とする。


## 11. 実装フェーズ

1. 基準値とバックアップ
2. 専用DB基盤
3. 既存データの一括移行
4. 内容照合
5. 継続同期
6. 読み取り切替
7. 書き込み元の切替
8. 旧書き込み停止と代表運用確認（30回の経過確認は完了後の通常運用）

各フェーズの成果物、完了条件、中止条件、切戻しは [DB集約 作業指示書](database-consolidation-work-instructions.md) に定める。

## 12. 検証方針の改訂（2026-09-16）

利用者の指示により、各フェーズは代表パターンで確認する。原則各1件、必要な境界例のみ最大3件。過去の成功試験を再利用し、全件照合・ハッシュ同一性を理由とする機械的な中断を廃止する。移行に影響しない差分は記録して続行し、実際の欠損・誤対応・部分保存・復元不能などは該当処理を修正する。

本項と [現行の検証基準](database-validation-policy.md) が旧資料の検証・停止・完了条件に優先する。移行対象の全データ保持、旧データの保持期間、同一要求の重複防止、履歴保持、業務単位の原子的保存は継続する。フェーズ5の完了結果は再利用し、フェーズ6へ進むための追加全件検証はしない。

## 13. フェーズ6の作業短縮（2026-09-16）

利用者の指示により、フェーズ6は共通読取りを一度実装し、各機能の接続・出力だけを確認する。既存の復旧・合格記録を再利用し、全件比較ツールの一括実行、全保存ファイルの再出力、機能ごとの完全コピー・復元・共通切戻し試験を追加しない。

n8nは保存済み入力を使い、実際の読取りノードからローカルDBサービスへの接続と直後の利用処理を確認すればよい。日次全体の通常運用1回や定刻実行待ちはフェーズ6の完了条件から外す。書込み切替・旧書込み停止を扱うフェーズ7・8の通常業務確認は維持する。

具体的な範囲・順序・記録方法は [作業指示書のフェーズ6](database-consolidation-work-instructions.md#13-フェーズ6-読み取り切替) に集約する。準備と実装後確認は合計15～30分を計画目安とし、実装時間は共通部分と各入口の差分で見積もる。時間を保証する条件ではなく、実際の不具合は該当範囲を修正する。今回の変更は指示書の改訂であり、フェーズ6の実行開始ではない。

### 読取り対応の実装範囲を限定（2026-09-16追記）

共通の参照元選択と、専用DBの値を既存入力形式へ変換する処理を共有する。記事・本文・レビュー等はAI入力／週次集計、台帳・評価等は確認アプリ／n8nで共用し、既存の表示・集計・判断処理を再利用する。n8nには既存ローカルDBサービスの必要な読取り口を追加する。各機能の集約対象の補助入力も切り替え、古い保存ファイルの再出力だけで完了扱いにしない。

具体的な再利用箇所と追加しない実装は作業指示書のフェーズ6に定める。実装は60～90分を計画目標とし、準備・受入確認は別枠。実測による保証ではなく、必要な取得・変換が不足する場合はその差分を示して更新する。今回も指示書の具体化であり、業務経路の切替は開始しない。


## フェーズ8での実装確定（2026-09-17）

旧Data Tablesと機械用JSON／JSONLは自動更新を停止した。必要時の互換出力と明示的な切戻しに備え、業務トランザクションに含めた不変な出力要求を専用DBへ保持する。自動反映の未完了と必要時出力の未送信を区別し、未送信を配信済みと扱わない。

008で停止設定と出力ごとの方針・先行要求参照を追加。元行、本文版、判断履歴、保留・競合の意味は変更しない。人向け出力と通常検証は専用DBを参照する。新規データを失わない切戻し・保存期間は [フェーズ8手順](database-phase8-retirement.md) に記載する。全件照合の再導入や30回運用待ちは完了条件にしない。
