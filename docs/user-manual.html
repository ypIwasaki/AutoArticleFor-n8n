GUIDE 01

最初に：目的に合う画面を開く

このマニュアルは、収集した記事を確認し、検索語と記事の採否を管理するための利用ガイドです。端末コマンドはWSLのプロジェクトルートで実行します。YYYY-MM-DD は対象日に置き換えてください。

検索語を整理する追加・編集・削除と候補の採用 →記事の採否を決める確認する観点と可・不可・保留 →今日の運用を進める収集からDB反映・確認まで →
画面主な用途開く
記事・タレント確認アプリ記事一覧、要約・分類、キーワード管理、記事評価8765 ↗
記事レビュー専用アプリ本文とレビュー欄を連続確認。Markdownへ保存8877 ↗
トークン比較アプリ作業日・工程ごとの観測使用量を比較8766 ↗
n8nワークフローと実行状況の確認5678 ↗

リンクは各アプリを起動してから使用します。レビュー専用アプリも既定は8765ですが、このガイドでは確認アプリと衝突しないよう8877を指定します。

初期設定・起動コマンド

初めての環境では n8n設定 に沿って設定・ワークフローの導入を済ませます。通常運用で毎回インポートし直す必要はありません。

python3 scripts/autoarticle_ops.py start n8n
python3 scripts/autoarticle_ops.py start dashboard
python3 scripts/article_review_viewer.py --port 8877
python3 apps/token-usage/server.py

手動で前面起動したサーバーは、その端末でCtrl+Cで停止できます。

参照: 確認アプリ · レビュー専用 · 比較アプリ

GUIDE 02

日次運用：取得後に成果物を確定する

  1. 対象日・作業範囲と既存実行を確認

    まずbriefで状態を確認。成功済みの収集があれば再利用します。

    python3 scripts/autoarticle_ops.py --date YYYY-MM-DD brief --scope full
  2. n8n起動・必要な収集・本文取得

    起動中なら30秒後にresume。再取得の終了、または次回へ繰り越す判断を待ちます。

  3. 記事作業と検証

    生成指示書に従い、共通本文確認→要約・人材索引・分類→キーワード・週次を作成。未確認記事は保留にし、確認済みの記録を再利用します。

  4. レビュー済み提案をDB反映

    各成果物をvalidate・checkpoint後、人材・記事関係→分類の順にapplyし、実DBと照合します。

  5. 最終画面を確認

    反映後に記事・要約・分類・週次をまとめて確認。画面上部のデータソースがDBか代替JSONか確認します。

工程の完了と、全記事の採用・人物の承認は別です。検索候補の採用や人物の検索有効化は、日次運用に自動で付随させません。

作業範囲の選択と詳細コマンド

prepare：起動準備 ／ articles：生成済み資料の記事作業 ／ articles-apply：記事作業・反映・表示 ／ full：全工程。状況照会だけなら status を使います。

工程別コマンドとcheckpointの詳細を参照してください。

参照: 運用開始 · 運用詳細

GUIDE 03

キーワードを追加・編集・削除する

確認アプリの「キーワード」ページを開き、まずどの保存先の語を変更するかを選びます。

区分操作反映先・タイミング
手動設定追加・編集・削除config/keywords.json。次回の通常収集で使用
n8n自動設定追加・編集・削除ワークフローのautoKeywords。次回の通常収集で使用
タレント登録読み取り専用approvedかつsearch_enabled=trueの人物名から生成
  1. 対象の区分を選び、語を入力して追加、または既存行を編集・削除します。
  2. 成功表示を確認し、一覧を再読み込みして変更を確認します。
  3. 同じ語が別区分に残っていないか確認します。一方を削除しても他方の語は残ります。

自動追加したくない語

excludedKeywords に設定します。手動設定の語はこれだけでは除去されません。検索対象から外したいときは手動設定も確認します。タレント由来の語も現行の日次ワークフローでは除外設定を参照します。

設定ファイルで管理する
{
  "manualKeywords": ["Vtuber", "にじさんじ"],
  "excludedKeywords": ["除外したい語"],
  "maxAutoKeywords": 30
}

既存項目を保持して編集し、JSONの末尾カンマは付けません。設定ファイルの変更だけならワークフロー再同期は不要です。Webhookで検索語を明示した収集では、その指定語が優先されます。

補正：旧文書の「rejected以外はすべて検索」は現行実装と異なります。承認状態と検索有効フラグの両方が必要です。

参照: 管理方法 · 現行ワークフロー

GUIDE 04

AI候補から検索語を採用する

  1. 確認アプリの「AI候補」を開き、最新日付・候補名・根拠を確認します。
  2. 継続して追う価値のある正式名称か、既存語と重複しないかを判断します。
  3. Add: yes の候補で追加ボタンが出ているものを採用します。
  4. 成功表示後、「キーワード」のn8n自動設定を確認します。
採用を検討見送りを検討
事務所・グループ・企業・継続プロジェクトの固有名一般語、名前の一部分、表記違い、単発の挨拶、無関係な攻略語

候補の作成だけでは検索設定に追加されません。最新候補以外、除外語、重複、上限到達では追加できない場合があります。Add: no は確認用です。

参照: 候補の判断基準 · 候補の追加

GUIDE 05

記事の有効性・採否を判断する

本文を取得できたこと、AI要約があること、人が採用したことは別の状態です。判断がつかない記事を無理に「可」にしません。

本文・元記事を確認→関連性・根拠・時点を確認→可 / 不可 / 保留 / 再取得
確認する点具体的に見るもの
検索テーマとの関連本文で対象人物や組織を扱っているか。関連記事欄・広告・同名の別人だけの一致ではないか
内容の確認可能性全文か一部か、メタデータだけか。動画の概要を動画本編の確認と扱っていないか
情報源と裏付け誰の発表か、原典や出典があるか。推測と事実が区別されているか
時点と新規性公開日だけでなく出来事の日付を確認。古い告知・再掲が現在のニュースに見えていないか

この確認観点は補足ガイドです。「何日前なら不可」という固定日数や、自動採否の新ルールを追加したものではありません。調査目的との関係で判断します。

状態選ぶ場面扱い
可 / approved必要な内容を確認し、調査に採用できる採用として反映
不可 / rejected明確な不採用理由がある理由必須
保留 / pendingまだ判断できない反映しない
再取得 / needs_refetch本文不足などで取り直したい専用レビューの再取得キューへ

不可理由の選び方

  • irrelevant：テーマと無関係。例：人物名が別人・地名として登場。
  • suspicious_source：配信元を除外候補にする。記事1本の誤りだけで媒体全体を不信と断定しない。
  • unavailable：内容を確認できない。回復が見込める一時的な取得失敗は保留・再取得も検討。
  • outdated：今回の調査では古い・再掲。古い資料でも背景説明に必要なら機械的に除外しない。

媒体不信による評価は週次集計で同媒体の別記事にも影響し得ます。根拠を確認して使います。

参照: 判定の定義 · 評価の集計への影響

GUIDE 06

方法A：確認アプリから評価を保存する

記事を1件ずつ見て、その場で評価を反映する方法です。

  1. 記事一覧から対象記事を開きます。
  2. 要約・分類・元記事を確認し、「記事評価」で「可」または「不可」を選びます。
  3. 不可なら「信頼できない情報源」「調査対象と無関係」「ページ削除・取得不能」「情報が古すぎる」から理由を選びます。
  4. 「評価を保存」を押し、成功表示を確認します。

この保存はn8nの評価Webhookへ送信します。下のレビュー専用アプリの「Markdown保存」とは異なります。n8nやDBへ接続できない場合、代替JSONが表示できても評価保存はできません。

この画面には保留・再取得の判定ボタンはありません。判断前なら保存せず、詳細レビュー・再取得を管理したい場合は方法Bを使います。

参照: 確認アプリ · 現行の評価操作

GUIDE 07

方法B：本文を連続レビューして一括反映する

レビュー専用アプリは、本文と判断メモをMarkdownに保存してからまとめて反映します。

1. 対象日のレビュー資料を用意

python3 scripts/capture_article_contents.py --run-date YYYY-MM-DD --retry-unverified
python3 scripts/generate_article_review_markdown.py --date YYYY-MM-DD --clean-generated

本文が既に揃っていれば不要な再取得を避けます。--clean-generated は自動参照を作り直し、記事正本のレビュー欄を維持します。

2. 画面を開いて保存

python3 scripts/article_review_viewer.py --port 8877
  1. 日付・キーワード・取得状態で絞り込みます。初期表示は未評価のみです。
  2. 「元記事」と抽出本文を確認。埋め込みできない記事は「外部で開く」を使います。
  3. 採否、キーワード取得、記事内容、不可理由、メモを記入します。
  4. 「保存して次へ」で進みます。過去の評価を見るには判定を「すべて」に変更します。

J / K 次・前、A 可、R 不可、Ctrl+Enter 保存して次へ、/ 検索。

3. ドライラン → 反映

python3 scripts/apply_article_markdown_reviews.py --date YYYY-MM-DD

対象件数・理由・エラーを確認した後に実行します。

python3 scripts/apply_article_markdown_reviews.py --date YYYY-MM-DD --apply

approved・rejectedがWebhookへ送信されます。pendingは無視され、needs_refetchは再取得キューへ出力されます。結果は content/article-review-results/YYYY-MM-DD.json で失敗件数も確認します。保存しただけではn8nへ反映されません。

再取得キューを処理する
python3 scripts/capture_article_contents.py --run-date YYYY-MM-DD --refetch-file content/article-refetch-requests/YYYY-MM-DD.jsonl
python3 scripts/generate_article_review_markdown.py --date YYYY-MM-DD --clean-generated

再取得した本文を確認し直してから判定を更新します。キューは --apply 実行時に出力されます。

Markdownを直接編集する場合
decision: pending
keyword_check: pending
content_check: pending
reason_code: ""
note: ""
reviewed_at: ""

記事正本のレビュー欄だけを編集します。本文や記事URLは書き換えません。キーワード・内容確認は pending / correct / incorrect / uncertain。レビュー時刻などの詳細は元文書を参照してください。

参照: 画面操作 · 生成・反映

GUIDE 08

評価を週次レポートへ反映する

記事評価を変更しても、保存済みの週次レポートが自動で書き換わるわけではありません。評価スナップショットを取得し、集計と考察を更新します。

python3 scripts/generate_article_feedback_instructions.py
python3 scripts/generate_analysis_reports.py --through YYYY-MM-DD
python3 scripts/read_ai_inputs.py --run-date YYYY-MM-DD --task weekly-report

確認済みの根拠から考察を編集した後に、数値反映・検証を行います。WEEK_STARTは対象週の月曜日です。

python3 scripts/generate_analysis_reports.py --through YYYY-MM-DD --sync-report content/weekly-reports/WEEK_START.md
python3 scripts/generate_analysis_reports.py --through YYYY-MM-DD --check --check-report content/weekly-reports/WEEK_START.md

後日の評価を過去週に適用するときは --as-of を揃えます。全件採否JSONが欠ける場合は暫定、収集日が欠ける場合は部分レポートとして扱います。0件と欠損は別です。

参照: 分析の詳細 · 週次の固定ルール

GUIDE 09

トークンの削減傾向を比較する

  1. 比較アプリを開き、基準日と比較日を選びます。
  2. 上部の非キャッシュ入力・出力・キャッシュ入力・合計を並べて見ます。
  3. 増減の分解を確認し、合計だけで削減失敗と判断しません。
  4. 未計測・未割当・試行回数を確認してから、工程別グラフを調べます。
  5. 工程検索・並べ替えで絞り込み、必要ならCSVを書き出します。新しい記録は再読み込みで取得します。

工程別の初期指標は非キャッシュ入力です。試行回数は記事数ではありません。異なる作業量の観測値なので、費用や施策の因果効果を直接示すものではありません。

計測記録を作るとき

現在のチャットのログをbindし、各工程の前にbegin、最後にfinishを実行します。環境にタスクIDがない場合、別タスクの最新ログを推測せず、接続手順を使います。

python3 scripts/autoarticle_ops.py --date YYYY-MM-DD tokens bind
python3 scripts/autoarticle_ops.py --date YYYY-MM-DD tokens begin summary
# 対象工程の作業・検証
python3 scripts/autoarticle_ops.py --date YYYY-MM-DD tokens finish

記録は content/operation-usage/。未観測分やfinish後の返答は含まれません。

参照: 計測 · 比較操作

GUIDE 10

困ったとき・状態の読み方

429・本文未取得・部分取得

取得は同時1件。Googleは30秒、記事サイトはホストごと10秒、全体2秒間隔です。429は最低1分、Retry-Afterや段階的バックオフが長ければそちらを優先。保存された再試行日時を守ります。状態ファイルを消して連打しません。未取得を本文確認済みに変更せず、他の記事の作業を進めます。

n8nが「起動中」のまま

30秒後にresumeで確認します。動いているプロセスを重複起動せず、継続して起動しない場合は記録された起動ログを確認します。

python3 scripts/autoarticle_ops.py --date YYYY-MM-DD resume
画面確認の再実行が必要か

成果物確定・DB反映後に最終表示を確認します。実確認から10分以内で成果物・画面コード・反映・起動記録が不変なら直後のresumeでは再利用できます。期限超過や変更時は再確認します。

別アプリが表示される / ポートが使用中

確認アプリ8765、レビュー専用8877、比較8766を使い分けます。レビュー専用を既定値で起動すると8765が競合します。

古い画面・保存失敗・DBではなくJSON表示

再読み込みし、対象日と画面上部のデータソースを確認します。代替JSON表示はDB反映の証明になりません。レビュー専用で同じMarkdownが他で更新された場合は再読込後に編集します。送信結果が不明な場合は実DB・結果ファイルを確認してから対応します。

Codexのsandbox初期化エラー

このWindows/WSL環境では、運用スキルに保存した承認付き実行経路を使います。通常sandboxの同じ初期化失敗を繰り返しません。権限審査そのものを迂回する設定ではありません。

参照: 運用と障害対応 · 運用スキル
